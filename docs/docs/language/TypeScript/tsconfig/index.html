tsconfig.json 은 어떤 파일을 검사할지, 얼마나 엄격하게 볼지, 어떤 JavaScript 를 만들지 정한다. tsc 는 지금 폴더의 tsconfig.json 을 읽고, 에디터도 같은 파일로 검사한다.

시작 설정

tsc --init 이 만드는 설정에 outDir · rootDir · include 를 더한 것이다. Node 에서 돌리는 프로젝트의 기본으로 쓴다.

{
  "compilerOptions": {
    // 무엇을 만들까
    "module": "nodenext",              // Node 의 ES 모듈 · CommonJS 규칙 그대로
    "target": "esnext",                // 문법을 바꾸지 않는다
    "types": ["node"],                 // 전역으로 읽을 @types — 적은 것만 읽는다
    "outDir": "dist",
    "rootDir": "src",
    "sourceMap": true,
    "declaration": true,               // .d.ts 도 만든다 (라이브러리)

    // 얼마나 엄격할까
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,

    // 다른 도구와 맞추기
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "moduleDetection": "force",
    "skipLibCheck": true
  },
  "include": ["src"]
}
  • tsconfig.json 은 주석 · 끝 쉼표가 되는 JSON(JSONC) 이다
  • include 를 빼면 폴더 아래 .ts 를 모두 읽는다. node_modules · outDir 은 알아서 뺀다

엄격한 옵션

옵션 막는 것 오류
strict 아래 여러 옵션을 한 번에 켠다 (strictNullChecks · noImplicitAny …) —
noImplicitAny (strict) 타입을 알 수 없는 매개변수 TS7006: Parameter 'x' implicitly has an 'any' type.
strictNullChecks (strict) null · undefined 일 수 있는 값을 그대로 쓰기 TS18048: 'user' is possibly 'undefined'.
noUncheckedIndexedAccess 배열 · 객체를 인덱스로 꺼낸 값을 있다고 믿기 TS18048: 'n' is possibly 'undefined'.
exactOptionalPropertyTypes 선택 속성(email?) 에 undefined 를 직접 넣기 TS2375: … with 'exactOptionalPropertyTypes: true'.
noUnusedLocals · noUnusedParameters 쓰지 않는 변수 · 매개변수 TS6133: 'x' is declared but its value is never read.
noImplicitReturns 어떤 갈래에서 return 을 빠뜨리기 TS7030: Not all code paths return a value. 
const notes: string[] = [];
const first = notes[0];            // noUncheckedIndexedAccess — string | undefined
first.length;                      // TS18048: 'first' is possibly 'undefined'.
first?.length;                     // 된다
  • 새 프로젝트는 처음부터 strict 를 켠다. 나중에 켜면 고칠 곳이 한꺼번에 쏟아진다
  • 옛 JavaScript 를 옮길 때는 strict: false 로 시작해 옵션을 하나씩 켠다. exactOptionalPropertyTypes 는 strictNullChecks 없이 켜면 TS5052 오류가 난다

module · target · lib

옵션 값 고르는 법
module nodenext Node 에서 돈다. package.json 의 type 을 따르고, 상대 경로 import 에 확장자를 쓴다
preserve 번들러(Vite · esbuild) 가 묶는다. import 를 손대지 않고, 확장자 없이 쓴다
target esnext · es2022 … 이보다 새 문법을 옛 문법으로 바꾼다. 번들러 · 최신 Node 면 esnext
lib ["esnext", "dom"] … 쓸 수 있는 전역 API 의 타입. 빼면 target 에 맞춰 DOM 까지 들어간다
types ["node"] · ["vite/client"] 전역으로 읽을 @types 패키지. 적지 않으면 아무것도 읽지 않는다 
import { Note } from "./types";
// TS2835: Relative import paths need explicit file extensions in ECMAScript imports
//         when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './types.js'?
  • nodenext 에서는 .ts 파일을 가져와도 확장자를 .js 로 쓴다(./types.js). 빌드한 뒤의 파일 이름이다
  • Node 로 바로 돌릴 때는 .ts 로 쓴다(./types.ts). 그러려면 "allowImportingTsExtensions": true 와 "noEmit": true 를, tsc 로 빌드도 하려면 "rewriteRelativeImportExtensions": true 를 준다 — 빌드하면 .js 로 바뀐다. 없으면 TS5097: An import path can only end with a '.ts' extension when 'allowImportingTsExtensions' is enabled. 가 난다
  • types 에 node 가 없으면 @types/node 를 설치했어도 TS2591: Cannot find name 'process'. Do you need to install type definitions for node? 가 난다. TypeScript 6 부터 types 를 적지 않으면 전역 타입을 하나도 읽지 않는다
  • 브라우저 코드에서 document 를 쓰는데 lib 에 dom 이 없으면 TS2584: Cannot find name 'document'. … Try changing the 'lib' compiler option to include 'dom'. 가 난다

다른 도구와 맞추기

옵션 하는 일
verbatimModuleSyntax 타입만 가져오는 import 에 type 을 쓰게 한다. 타입을 지우는 도구(Node · esbuild) 가 import 를 그대로 남겨도 안전하다
isolatedModules 파일 하나만 보고 바꿀 수 없는 문법(다른 파일의 const enum 등) 을 막는다
erasableSyntaxOnly 지워서 없어지지 않는 문법(enum · namespace · 생성자의 private x) 을 막는다. Node 로 바로 돌릴 때 켠다
skipLibCheck node_modules 의 .d.ts 는 검사하지 않는다. 빨라지고, 라이브러리끼리의 타입 충돌을 피한다
moduleDetection: "force" import · export 가 없는 파일도 모듈로 본다. 파일끼리 전역 이름이 부딪히지 않는다 
import { Note } from "./types.ts";
// TS1484: 'Note' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
import type { Note } from "./types.ts";      // 된다
import { type Note, VERSION } from "./types.ts";   // 값과 섞을 때

설정 나누기

extends 로 공통 설정을 물려받는다. 빌드용 · 테스트용처럼 조금만 다른 설정을 둘 때 쓴다.

// tsconfig.build.json — npx tsc -p tsconfig.build.json
{
  "extends": "./tsconfig.json",
  "compilerOptions": { "noEmit": false, "sourceMap": false },
  "exclude": ["src/**/*.test.ts"]
}
  • 많이 쓰는 기본 설정은 패키지로도 있다: npm install -D @tsconfig/node24 뒤 "extends": "@tsconfig/node24/tsconfig.json"

프로젝트 나누기

한 저장소에 패키지가 여럿이면(모노레포) 패키지마다 tsconfig.json 을 두고 references 로 잇는다. tsc -b 가 의존 순서대로 빌드하고, 바뀌지 않은 패키지는 건너뛴다.

tsconfig.json              { "files": [], "references": [{ "path": "packages/core" }, { "path": "packages/app" }] }
packages/core/tsconfig.json  { "extends": "../../tsconfig.base.json", "compilerOptions": { "composite": true, "outDir": "dist" } }
packages/app/tsconfig.json   { "extends": "../../tsconfig.base.json", "references": [{ "path": "../core" }] }
npx tsc -b              # core → app 순서로
npx tsc -b --verbose    # 무엇을 다시 빌드하고 무엇을 건너뛰는지
npx tsc -b --clean      # 만든 것 지우기
  • 가리켜지는 쪽(core) 은 "composite": true 가 있어야 한다. .d.ts 와 tsconfig.tsbuildinfo 를 만들어 다음 빌드에서 바뀐 것만 본다
