타입은 이름: 타입 으로 적는다. 초기값이 있으면 TypeScript 가 타입을 알아서 추론하므로, 적는 곳은 주로 함수 매개변수 · 반환 값 · 빈 값으로 시작하는 변수 · 객체 모양이다.

원시 타입 · 추론

let title = "메모";                // string 으로 추론
const kind = "memo";               // "memo" — const 는 바뀌지 않으니 글자 그대로의 타입
let total: number = 0;
total = "10";                      // TS2322: Type 'string' is not assignable to type 'number'.

let big = 10n;                     // bigint
let ok = true;                     // boolean
let id = Symbol("id");             // symbol
  • 원시 타입은 소문자로 쓴다(string · number · boolean). 대문자 String 은 래퍼 객체 타입이라 쓰지 않는다
  • 추론이 맞으면 적지 않는다. 적으면 고칠 곳만 늘어난다

배열 · 튜플

const tags: string[] = ["a", "b"];
const scores: Array<number> = [90, 85];          // 같은 뜻
const matrix: number[][] = [[1, 2], [3, 4]];

let entry: [string, number] = ["kim", 3];        // 튜플 — 자리마다 타입과 개수가 정해진다
entry = ["kim", "3"];                            // TS2322: Type 'string' is not assignable to type 'number'.
const [name, count] = entry;                     // string, number

const point: readonly [number, number] = [0, 0]; // 고칠 수 없는 튜플

객체

type Note = {
  id: number;
  text: string;
  pinned?: boolean;                  // 없어도 된다 — boolean | undefined
  readonly createdAt: Date;          // 만든 뒤 바꿀 수 없다
};

const note: Note = { id: 1, text: "장보기", createdAt: new Date() };
note.createdAt = new Date();         // TS2540: Cannot assign to 'createdAt' because it is a read-only property.

const typo: Note = { id: 2, txt: "x", createdAt: new Date() };
// TS2561: Object literal may only specify known properties, but 'txt' does not exist in type 'Note'.
//         Did you mean to write 'text'?
  • 객체 리터럴을 바로 넣을 때만 모르는 속성을 오류로 본다. 변수에 담았다가 넘기면 속성이 더 있어도 통과한다(구조적 타이핑)
  • readonly 는 타입 검사에서만 막는다. 실행 중에 고정하려면 Object.freeze 를 쓴다

유니온 · 리터럴

| 로 "이것 또는 저것" 을 만든다. 글자 · 숫자 그대로를 타입으로 쓰면(리터럴 타입) 정해진 값만 받는다.

type Id = number | string;
type Status = "draft" | "published" | "archived";

let s: Status = "draft";
s = "drft";      // TS2820: Type '"drft"' is not assignable to type 'Status'. Did you mean '"draft"'?

function show(id: Id) {
  return id.toUpperCase();
  // TS2339: Property 'toUpperCase' does not exist on type 'Id'.
  //   Property 'toUpperCase' does not exist on type 'number'.
}
  • 유니온은 모든 갈래에 있는 것만 바로 쓴다. 한 갈래의 것을 쓰려면 먼저 좁힌다(typeof id === "string")
  • 문자열 리터럴 유니온은 enum 대신 쓴다. 지워서 없어지는 타입이라 그대로 JavaScript 가 된다

null · undefined

strictNullChecks(strict) 를 켜면 null · undefined 는 따로 적어야 들어간다.

let user: { name: string } | null = null;
user.name;                                  // TS18047: 'user' is possibly 'null'.
user?.name;                                 // 된다 — string | undefined

const el = document.querySelector("#app");  // Element | null
el.textContent = "x";                       // TS18047: 'el' is possibly 'null'.
if (el) el.textContent = "x";               // 된다
el!.textContent = "x";                      // ! — "null 이 아니다" 라고 우긴다. 틀리면 실행 중에 터진다
  • ! 은 바로 앞에서 확인한 것처럼 확실할 때만 쓴다. 대개 if · ?. · ?? 로 처리한다

any · unknown · never

타입 뜻 쓰는 곳
any 검사를 끈다. 무엇이든 넣고 무엇이든 부른다 옮기는 중인 옛 코드. 새 코드에서는 쓰지 않는다
unknown 무엇이든 들어오지만, 좁히기 전에는 쓸 수 없다 JSON.parse 결과 · catch (e) · 밖에서 온 값
never 값이 있을 수 없다 늘 던지는 함수의 반환 · 모든 경우를 처리했는지 검사 
const data: unknown = JSON.parse(text);
data.id;                                    // TS18046: 'data' is of type 'unknown'.
if (typeof data === "object" && data !== null && "id" in data) data.id;   // 좁힌 뒤에 쓴다

function fail(message: string): never {
  throw new Error(message);
}
  • catch (e) 의 e 는 unknown 이다. e instanceof Error 로 확인하고 e.message 를 쓴다

type 과 interface

객체 모양은 둘 다로 쓴다.

type Animal = { name: string };
type Dog = Animal & { bark(): void };              // & 로 합친다

interface Pet { name: string }
interface Cat extends Pet { meow(): void }         // extends 로 넓힌다

interface Shape { name: string }
interface Shape { color: string }                  // 같은 이름은 합쳐진다
const box: Shape = { name: "box" };                // TS2741: Property 'color' is missing … but required in type 'Shape'.
type interface
객체 모양 된다 된다
유니온 · 튜플 · 원시 타입 이름 된다 (type Id = number | string) 안 된다
넓히기 & extends
같은 이름 두 번 오류 합쳐진다
  • 하나로 정해 쓴다. type 으로 모두 되고 뜻밖에 합쳐지는 일이 없어 type 을 기본으로 쓰는 쪽이 많다. 라이브러리가 사용자에게 넓힐 자리를 줄 때(전역 · 플러그인 타입) 는 interface 를 쓴다
  • & 로 같은 속성을 서로 다른 타입으로 합치면 그 속성은 never 가 된다: { a: string } & { a: number } 의 a 에는 아무것도 넣을 수 없다
