Java 는 오류를 예외로 던지고 try · catch 로 받는다. 예외는 컴파일러가 처리를 강제하는 checked 예외(IOException …) 와 강제하지 않는 unchecked 예외(RuntimeException 의 자식) 로 나뉜다. 닫아야 하는 자원은 try-with-resources 로 연다.

던지고 받기

try {
    Files.readString(Path.of("nope.txt"));
} catch (NoSuchFileException e) {              // 구체적인 것부터
    IO.println("파일이 없다: " + e.getMessage());
} catch (IOException e) {                      // 더 넓은 것
    IO.println("읽지 못했다: " + e);
} finally {
    IO.println("늘 돈다");                     // 예외가 나든 return 하든
}

try { … } catch (ClassCastException | NumberFormatException e) { … }   // 여럿을 한 번에

잡지 않은 예외는 호출 스택을 찍고 프로그램을 끝낸다.

Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 2 out of bounds for length 1
	at Un.main(Un.java:1)

checked 와 unchecked

종류 예 컴파일러
checked (Exception 의 자식) IOException · SQLException · InterruptedException 잡거나 throws 로 선언해야 한다
unchecked (RuntimeException 의 자식) NullPointerException · IllegalArgumentException · IllegalStateException · IndexOutOfBoundsException 강제하지 않는다
Error OutOfMemoryError · StackOverflowError 잡지 않는다 
Files.readString(Path.of("x"));
// error: unreported exception IOException; must be caught or declared to be thrown

String read(Path p) throws IOException {       // 처리하지 않고 부른 쪽에 넘긴다
    return Files.readString(p);
}
  • 호출한 쪽이 실제로 대처할 수 있는 실패(파일 없음 · 네트워크) 는 checked, 프로그래머의 실수(잘못된 인자 · 상태) 는 unchecked 로 던진다
  • 람다 · 스트림 안에서는 checked 예외를 던질 수 없다. 안에서 잡아 UncheckedIOException 으로 감싸 던진다

내 예외 만들기 · 감싸기

class NotFoundException extends RuntimeException {
    NotFoundException(String what) { super("찾지 못했다: " + what); }
}

class ConfigException extends Exception {
    ConfigException(String message, Throwable cause) { super(message, cause); }
}

String readConfig(Path p) throws ConfigException {
    try {
        return Files.readString(p);
    } catch (IOException e) {
        throw new ConfigException("설정을 읽지 못했다: " + p, e);   // 원래 예외를 cause 로 붙인다
    }
}
// 설정을 읽지 못했다: nope.conf / 원인: NoSuchFileException nope.conf
  • 감쌀 때는 원래 예외를 꼭 cause 로 넘긴다. 빼면 처음 어디서 왜 났는지 스택이 사라진다
  • catch (Exception e) {} 처럼 빈 칸으로 삼키지 않는다. 최소한 로그를 남긴다

try-with-resources

AutoCloseable 인 자원은 괄호 안에서 열면 블록을 나갈 때 거꾸로 닫힌다. 예외가 나도 닫힌다.

try (var reader = Files.newBufferedReader(Path.of("notes.txt"));
     var writer = Files.newBufferedWriter(Path.of("out.txt"))) {
    writer.write(reader.readLine());
}                                              // writer, reader 순서로 닫힌다

class Res implements AutoCloseable {
    @Override public void close() { … }        // 내 자원도 이렇게 만든다
}

잡음 중간 실패
  • finally 에서 close() 를 직접 부르는 옛 방식은 close 가 다시 던지면 원래 예외를 덮어쓴다. try-with-resources 는 원래 예외를 남기고 close 의 것은 getSuppressed() 에 붙인다

NullPointerException

가장 흔한 예외다. 메시지가 무엇이 null 이었는지 알려 준다.

Cannot invoke "String.length()" because "s" is null
  • 변수 이름은 디버그 정보가 있을 때(javac -g, IDE · Maven · Gradle 빌드) 나온다. java File.java 로 바로 돌리면 "<local1>" 처럼 나온다
  • 받은 인자는 Objects.requireNonNull(x, "x") 로 들어오는 곳에서 막는다. 없을 수 있는 반환 값은 Optional 로 돌려준다

예전에는

  • 자원을 try { … } finally { if (r != null) r.close(); } 로 닫았다. Java 7 부터 try-with-resources 다
  • catch (IOException e) { … } catch (SQLException e) { … } 로 같은 처리를 되풀이했다. Java 7 부터 | 로 묶는다
  • NullPointerException 은 줄 번호만 알려 줬다. Java 14 부터 무엇이 null 인지 알려 준다
