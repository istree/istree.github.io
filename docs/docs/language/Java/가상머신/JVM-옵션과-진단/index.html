JVM 은 실행 중에 바이트코드를 기계어로 바꾸고(JIT), 쓰지 않는 객체를 알아서 치운다(GC). 대부분은 기본값으로 충분하고, 메모리 크기 · GC 를 바꿀 때만 옵션을 준다. 느리거나 멈추거나 메모리가 새면 JDK 에 들어 있는 jcmd · JFR 로 실행 중인 프로세스를 들여다본다.

메모리

java -Xms512m -Xmx2g -jar app.jar             # 힙 처음 · 최대 크기
java -XX:MaxRAMPercentage=75 -jar app.jar     # 컨테이너 메모리의 75% 를 최대 힙으로
java -XshowSettings:vm -version               # 지금 설정 — Max. Heap Size (Estimated): 4.00G
  • 힙 최대값을 주지 않으면 물리 메모리(컨테이너면 그 한도) 의 1/4 이다. 16 GB 맥에서 4 GB 다
  • 컨테이너에서는 -Xmx 대신 MaxRAMPercentage 로 준다. 컨테이너 크기를 바꿔도 따라간다
  • 힙이 모자라면 java.lang.OutOfMemoryError: Java heap space 로 멈춘다. 늘 늘리기 전에 무엇이 메모리를 잡고 있는지 본다(아래 힙 덤프)

GC

GC 옵션 쓰는 곳
G1 기본 (-XX:+UseG1GC) 대부분 — 처리량과 멈춤의 균형
ZGC -XX:+UseZGC 큰 힙 · 멈춤을 1 ms 아래로
Parallel -XX:+UseParallelGC 일괄 처리 — 멈춰도 되고 처리량이 중요할 때
Serial -XX:+UseSerialGC 작은 컨테이너 · CPU 하나 
java -Xlog:gc:file=gc.log -jar app.jar        # GC 로그
[0.003s][info][gc] Using G1
[3.036s][info][gc] GC(0) Pause Young (Concurrent Start) (G1 Humongous Allocation) 44M->29M(64M) 5.362ms
  • 로그 한 줄은 GC 종류 · 정리 전 → 후 크기(전체) · 멈춘 시간이다. 멈춤이 길고 잦으면 힙 크기 · GC 를 바꿔 본다

jcmd — 실행 중인 JVM 보기

jcmd                                  # 돌고 있는 JVM 목록 — pid 와 메인 클래스
jcmd <pid> VM.version
jcmd <pid> VM.flags                   # 적용된 옵션
jcmd <pid> GC.heap_info               # garbage-first heap total reserved 65536K, committed 65536K, used 3198K …
jcmd <pid> Thread.print               # 스레드 덤프 (= jstack <pid>)
jcmd <pid> GC.heap_dump heap.hprof    # 힙 덤프
  • 멈춘 것처럼 보이면 스레드 덤프를 몇 초 사이로 두세 번 떠서 견준다. 계속 같은 줄에 있는 스레드가 범인이다
  • "main" #3 … waiting on condition 처럼 스레드마다 상태(RUNNABLE · WAITING · BLOCKED) 와 스택이 나온다. BLOCKED 가 많으면 잠금을 다툰다

힙 덤프 — 메모리 누수 찾기

메모리가 모자라 죽을 때 그 순간의 힙을 파일로 남기게 해 둔다.

java -Xmx64m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=heap.hprof -jar app.jar
java.lang.OutOfMemoryError: Java heap space
Dumping heap to heap.hprof ...
Heap dump file created [39048650 bytes in 0.031 secs]
  • .hprof 는 Eclipse MAT · VisualVM · IntelliJ 로 연다. 크기가 큰 객체와 그것을 붙잡고 있는 참조(GC root 까지의 길) 를 본다
  • 운영 서버에는 HeapDumpOnOutOfMemoryError 를 늘 켜 둔다. 다시 일어나기를 기다리지 않아도 된다

JFR — 실행 기록

Java Flight Recorder 는 CPU · 메모리 · GC · 잠금 · I/O 를 거의 부담 없이 기록한다. 운영 중에도 켠다.

java -XX:StartFlightRecording=filename=rec.jfr,settings=profile -jar app.jar   # 시작부터 기록
jcmd <pid> JFR.start duration=60s filename=rec.jfr                            # 돌고 있는 것을 60 초

$JAVA_HOME/bin/jfr summary rec.jfr                                # 이벤트 종류 · 개수
$JAVA_HOME/bin/jfr print --events jdk.ExecutionSample rec.jfr     # CPU 를 쓴 곳의 스택
  • 그래프로는 JDK Mission Control(JMC) · IntelliJ 의 프로파일러로 연다
  • jfr 명령은 macOS 의 /usr/bin 에 없다. $JAVA_HOME/bin 을 PATH 에 넣거나 경로째 부른다

예전에는

  • -XX:PermSize · -XX:MaxPermSize 로 클래스 영역(PermGen) 을 정했다. Java 8 부터 Metaspace 로 바뀌어 보통 정하지 않는다
  • 기본 GC 는 Parallel 이었다. Java 9 부터 G1 이다. CMS 는 Java 14 에서 빠졌다
  • 컨테이너 안의 JVM 이 호스트 전체 메모리를 보고 힙을 잡아 컨테이너가 죽었다. Java 10(8u191) 부터 컨테이너 한도를 읽는다
  • JFR 은 Oracle JDK 의 유료 기능이었다. Java 11 부터 OpenJDK 에 들어 있다
