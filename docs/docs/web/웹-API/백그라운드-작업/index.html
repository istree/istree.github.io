브라우저의 JavaScript 는 화면을 그리는 스레드(메인 스레드) 하나에서 돈다. 여기서 오래 걸리는 계산을 하면 그동안 클릭 · 스크롤 · 그리기가 모두 멈춘다. 무거운 계산은 Web Worker 로 다른 스레드에 보내고, 네트워크 가로채기 · 오프라인 · 푸시는 서비스 워커가 쪽 밖에서 맡는다.

Web Worker

// worker.js — 300 만 아래의 소수 세기
self.onmessage = (e) => {
  const n = e.data;
  let count = 0;
  for (let i = 2; i < n; i++) {
    let prime = true;
    for (let j = 2; j * j <= i; j++) if (i % j === 0) { prime = false; break; }
    if (prime) count++;
  }
  self.postMessage(count);
};
// 쪽
const worker = new Worker("/worker.js", { type: "module" });   // module 이면 import 를 쓴다
worker.onmessage = (e) => console.log(e.data);                  // 216816
worker.onerror = (e) => console.error(e.message);
worker.postMessage(3_000_000);
worker.terminate();                                             // 다 쓰면 끈다

같은 계산을 10ms 마다 도는 타이머와 함께 돌려 보면 차이가 보인다.

어디서 걸린 시간 그동안 타이머가 돈 횟수
Worker 510ms 50 — 화면은 계속 응답한다
메인 스레드 416ms 0 — 그동안 쪽이 멈췄다
  • Worker 안에는 document · window 가 없다. DOM 은 못 만지고 fetch · IndexedDB · OffscreenCanvas · setTimeout 은 된다
  • 주고받는 값은 복사된다(structured clone). 큰 ArrayBuffer 는 넘기면(transfer) 복사 없이 옮겨지고, 보낸 쪽의 것은 비게 된다
const buf = new ArrayBuffer(8 * 1024 * 1024);
worker.postMessage(buf, [buf]);    // 받은 쪽 byteLength 8388608, 보낸 쪽 buf.byteLength 0
  • 큰 CSV · JSON 읽기, 그림 처리, 압축 · 암호, 검색 색인 만들기, Wasm 돌리기에 쓴다
  • 메시지를 주고받는 코드가 번거로우면 Comlink 로 함수 부르듯 쓴다

탭끼리

const ch = new BroadcastChannel("todo");          // 같은 출처의 탭 · 창 · 워커 모두
ch.postMessage({ type: "saved", id: 3 });
ch.onmessage = (e) => e.data;                      // 다른 탭에서 {type: "saved", id: 3}
  • 한 탭에서 로그아웃하면 다른 탭도 로그인 쪽으로 보내는 일 · 목록을 다시 읽게 하는 일에 쓴다

쉴 때 · 나눠서

requestIdleCallback((deadline) => {                // 브라우저가 한가할 때 — 기록 보내기 · 미리 계산
  while (deadline.timeRemaining() > 0 && queue.length) work(queue.shift());
}, { timeout: 1000 });

for (const item of bigList) {                      // 긴 반복을 잘게 나눠 화면에 차례를 준다
  process(item);
  await scheduler.yield();                         // 없는 브라우저에서는 setTimeout 으로 대신
}

서비스 워커

쪽과 네트워크 사이에 끼어 요청을 가로챈다. 캐시에서 답하면 오프라인에서도 쪽이 열린다.

// sw.js
const CACHE = "app-v1";
self.addEventListener("install", (e) => {
  e.waitUntil(caches.open(CACHE).then((c) => c.addAll(["/", "/app.js", "/offline.txt"])));
  self.skipWaiting();                              // 새 판을 바로 쓴다
});
self.addEventListener("activate", (e) => e.waitUntil(self.clients.claim()));
self.addEventListener("fetch", (e) => {
  e.respondWith(
    caches.match(e.request)                        // 캐시에 있으면 그것
      .then((hit) => hit || fetch(e.request))      // 없으면 네트워크
      .catch(() => caches.match("/offline.txt"))   // 네트워크도 안 되면 오프라인 안내
  );
});
// 쪽
await navigator.serviceWorker.register("/sw.js");  // scope — sw.js 가 있는 폴더 아래 쪽만 맡는다
await fetch("/offline.txt");                       // 200 "오프라인이다" — 캐시에서
await fetch("http://127.0.0.1:1/api");             // 서버가 없어도 200 "오프라인이다"
  • https(또는 localhost · 127.0.0.1) 에서만 등록된다
  • 처음 연 쪽은 서비스 워커가 맡지 않는다. clients.claim() 을 하거나 다시 열어야 맡는다
  • 새 sw.js 를 배포하면 옛 워커를 쓰는 탭이 다 닫힐 때까지 기다린다. 캐시 이름(app-v1) 을 올리고 activate 에서 옛 캐시를 지운다
  • 손으로 짜면 캐시 꼬임이 잦다. Workbox · vite-plugin-pwa 로 만든다
  • 개발자 도구 Application › Service workers 에서 "Update on reload" 를 켜 두면 고칠 때마다 새로 깔린다

예전에는

  • 무거운 계산을 setTimeout(fn, 0) 으로 잘게 나눠 화면에 차례를 줬다. 지금도 쓰지만 scheduler.yield() 가 차례를 덜 잃는다
  • 오프라인은 AppCache 로 했다. 한 번 잘못 캐시하면 풀 수 없어 없어졌다
