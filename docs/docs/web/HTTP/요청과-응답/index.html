HTTP 의 한 번 주고받기는 요청 하나와 응답 하나다. 요청은 "메서드 · 경로 · 헤더 · 본문", 응답은 "상태 코드 · 헤더 · 본문" 으로 되어 있고, HTTP/1.1 에서는 이것이 사람이 읽을 수 있는 글자로 오간다. 아래 예는 할 일 API 를 만든 작은 서버에 curl 로 보낸 실제 메시지다.

메시지

$ curl -v http://127.0.0.1:8801/api/todos
> GET /api/todos HTTP/1.1                        ← 요청 줄: 메서드 · 경로 · 판
> Host: 127.0.0.1:8801                           ← 요청 헤더
> User-Agent: curl/8.7.1
> Accept: */*
>                                                ← 빈 줄 — 헤더 끝 (GET 은 본문이 없다)
< HTTP/1.1 200 OK                                ← 상태 줄: 판 · 코드 · 이유
< Content-Type: application/json; charset=utf-8  ← 응답 헤더
< ETag: "cIgZsr1sIr46"
< Cache-Control: no-cache
< Date: Sun, 08 Nov 2026 04:24:57 GMT
< Connection: keep-alive
< Transfer-Encoding: chunked
<
[{"id":1,"title":"우유 사기","done":false}]      ← 본문
  • > 는 보낸 것, < 는 받은 것이다. curl -i 는 응답 헤더만, curl -v 는 둘 다 보인다
  • 브라우저에서는 개발자 도구의 네트워크 탭에서 같은 것을 본다

메서드

메서드 뜻 본문 여러 번 보내도 같나
GET 가져오기 없음 같다
POST 만들기 · 그 밖의 처리 있음 아니다 — 두 번 보내면 둘이 생긴다
PUT 통째로 바꾸기 (없으면 만들기) 있음 같다
PATCH 일부 바꾸기 있음 경우에 따라
DELETE 지우기 보통 없음 같다
HEAD 헤더만 가져오기 없음 같다
OPTIONS 되는 것 묻기 — CORS 사전 요청 없음 같다 
$ curl -i -b jar -X POST -H 'Content-Type: application/json' -d '{"title":"책 읽기"}' http://127.0.0.1:8801/api/todos
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/todos/2                           ← 새로 만든 것의 주소

{"id":2,"title":"책 읽기","done":false}

$ curl -X PUT -H 'Content-Type: application/json' -d '{"done":true}' http://127.0.0.1:8801/api/todos/1
{"id":1,"title":"우유 사기","done":true}

$ curl -i -X DELETE http://127.0.0.1:8801/api/todos/2
HTTP/1.1 204 No Content                          ← 됐고 돌려줄 본문은 없다
  • GET 으로 무언가를 바꾸지 않는다. 검색 엔진 · 미리 받기(prefetch) 가 링크를 따라가며 GET 을 보낸다
  • "여러 번 보내도 같다(멱등)" 는 메서드는 연결이 끊겼을 때 브라우저 · 라이브러리가 다시 보내도 안전하다. POST 를 다시 보낼 때는 Idempotency-Key 헤더 같은 장치를 둔다

주소

https://api.example.com:8443/todos/7?done=false&sort=due#memo 는 이렇게 나뉜다.

부분 값
scheme https
host api.example.com
port 8443 (https 의 기본은 443)
path /todos/7
query done=false&sort=due
fragment memo 
const u = new URL("https://api.example.com:8443/todos/7?done=false&sort=due#memo");
u.origin;                      // "https://api.example.com:8443"
u.searchParams.get("sort");    // "due"
  • # 뒤(fragment) 는 서버에 가지 않는다. 쪽 안의 위치 · 화면 상태에 쓴다
  • 출처(origin) 는 scheme · host · port 셋이다. 셋 중 하나라도 다르면 다른 출처다 — CORS · 쿠키가 이것으로 갈린다
  • 쿼리의 한글 · 공백은 %ED%95%9C 처럼 바꿔 보낸다. 스크립트에서는 new URLSearchParams({ q: "한글 검색" }) 이 해 준다

본문의 형식

Content-Type 본문
application/json {"title":"책 읽기"} — API
application/x-www-form-urlencoded title=%EC%B1%85&done=false — HTML 폼 기본
multipart/form-data; boundary=… 칸마다 나눈 덩어리 — 파일 올리기
text/html; charset=utf-8 쪽
  • 서버는 Content-Type 을 보고 본문을 읽는다. JSON 을 보내며 이 헤더를 빠뜨리면 서버가 읽지 못한다 — 위 서버는 400 {"error":"JSON 이 아니다"} 로 답한다
  • 받고 싶은 형식은 Accept: application/json 으로 알린다

HTTP/1.1 · 2 · 3

판 오가는 꼴 특징
HTTP/1.1 글자 연결 하나에 한 번에 요청 하나 — 브라우저는 출처마다 연결 6 개를 연다
HTTP/2 이진 프레임 (TLS 위) 연결 하나에 요청 여럿을 섞어 보낸다 · 헤더를 줄인다
HTTP/3 이진 프레임 (QUIC · UDP 위) 패킷 하나가 늦어도 다른 요청이 기다리지 않는다 · 연결이 빠르다 
$ curl -sI https://example.com
HTTP/2 200
alt-svc: h3=":443"; ma=86400                     ← "HTTP/3 도 된다" 는 안내
  • 판이 바뀌어도 메서드 · 상태 코드 · 헤더의 뜻은 같다. 코드는 판을 신경 쓰지 않는다
  • HTTP/2 부터 헤더 이름은 모두 소문자로 오간다

예전에는

  • HTTP/1.1 에서 요청 수를 줄이려고 그림을 한 장으로 붙이고(스프라이트), JS · CSS 를 하나로 합치고, 도메인을 나눠(sharding) 연결을 늘렸다. HTTP/2 부터는 대부분 필요 없다
  • X-HTTP-Method-Override 헤더로 PUT · DELETE 를 POST 에 실어 보냈다. 지금은 그대로 보낸다
