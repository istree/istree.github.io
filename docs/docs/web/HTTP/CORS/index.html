CORS(Cross-Origin Resource Sharing) 는 다른 출처의 서버가 "이 출처의 스크립트는 내 응답을 읽어도 된다" 고 허락하는 방법이다. 브라우저는 기본으로 다른 출처에 보낸 fetch 의 응답을 스크립트가 읽지 못하게 막는다(동일 출처 정책). 서버가 응답에 Access-Control-Allow-Origin 헤더를 붙여야 읽힌다. 아래 예는 http://127.0.0.1:8802 의 쪽에서 http://127.0.0.1:8801 의 API 를 부른 것이다 — 포트가 달라 다른 출처다.

막힐 때

// http://localhost:8802 에서 — 서버가 허락한 출처는 http://127.0.0.1:8802 뿐이다
await fetch("http://127.0.0.1:8801/api/todos");
// TypeError: Failed to fetch
Access to fetch at 'http://127.0.0.1:8801/api/todos' from origin 'http://localhost:8802' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
  • 서버 기록에는 GET /api/todos Origin=http://localhost:8802 가 남는다. 요청은 가고 처리도 됐지만, 브라우저가 응답을 스크립트에 넘기지 않은 것이다
  • 스크립트에는 TypeError: Failed to fetch 만 온다. 까닭은 콘솔에만 나온다
  • localhost 와 127.0.0.1 도 다른 출처다
  • curl · 서버끼리의 요청에는 CORS 가 없다. 브라우저가 사용자를 지키려고 하는 검사다

허락하기

HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://127.0.0.1:8802      ← 이 출처는 읽어도 된다
Vary: Origin                                             ← 출처마다 응답이 다르다 — 캐시가 섞이지 않게
// Node 서버 — 허락할 출처 목록에 있으면 그 출처를 돌려준다
const ALLOW = new Set(["http://127.0.0.1:8802", "https://app.example.com"]);
if (ALLOW.has(req.headers.origin)) {
  res.setHeader("Access-Control-Allow-Origin", req.headers.origin);
  res.setHeader("Vary", "Origin");
}
  • 아무나 읽어도 되는 공개 API 는 Access-Control-Allow-Origin: * 다. 단 쿠키를 함께 보내는 요청에는 * 가 통하지 않는다
  • 허락할 출처는 목록으로 견준다. 요청의 Origin 을 그대로 돌려주면 모든 사이트에 허락한 것과 같다

사전 요청

GET · POST(폼 형식) 같은 단순한 요청이 아니면, 브라우저가 본 요청 전에 OPTIONS 로 먼저 묻는다.

await fetch("http://127.0.0.1:8801/api/todos/1", {
  method: "PUT",
  headers: { "Content-Type": "application/json" },     // JSON · PUT · 내 헤더 — 사전 요청이 간다
  body: JSON.stringify({ done: true }),
});
서버 기록:
OPTIONS /api/todos/1 Origin=http://127.0.0.1:8802     ← 사전 요청
PUT /api/todos/1 Origin=http://127.0.0.1:8802         ← 허락을 받은 뒤 본 요청
$ curl -i -X OPTIONS -H "Origin: http://127.0.0.1:8802" \
       -H "Access-Control-Request-Method: PUT" -H "Access-Control-Request-Headers: content-type" \
       http://127.0.0.1:8801/api/todos/1
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://127.0.0.1:8802
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type
Access-Control-Max-Age: 600                              ← 10 분 동안 다시 묻지 않는다
사전 요청이 가는 때 예
메서드가 GET · HEAD · POST 가 아니다 PUT · DELETE · PATCH
Content-Type 이 폼 · 글자가 아니다 application/json
내 헤더를 붙였다 Authorization · X-Request-Id
  • OPTIONS 에 404 · 401 을 주면 본 요청이 가지 않는다. 인증 검사보다 앞에서 OPTIONS 를 받아 준다

쿠키와 함께

await fetch("http://127.0.0.1:8801/me");                              // 401 — 쿠키가 가지 않는다
await fetch("http://127.0.0.1:8801/login", { method: "POST", credentials: "include" });
await fetch("http://127.0.0.1:8801/me", { credentials: "include" });   // 200 {"user":"geon"}
  • 다른 출처로는 credentials: "include" 를 줘야 쿠키를 보내고 받는다
  • 서버는 Access-Control-Allow-Credentials: true 와 * 가 아닌 출처를 함께 보내야 한다

피하는 길

  • 개발 중에는 개발 서버의 프록시(Vite 의 server.proxy) 로 API 를 같은 출처처럼 부른다
  • 운영에서는 Nginx 가 /api 를 백엔드로 넘겨 같은 출처로 맞추면 CORS 가 필요 없다
  • mode: "no-cors" 는 막힘을 푸는 것이 아니다. 요청은 가지만 응답은 비어 있다(type: "opaque", status: 0)

예전에는

  • 다른 출처의 데이터를 <script src="…?callback=f"> 로 받는 JSONP 를 썼다. GET 만 되고 그 서버의 스크립트를 그대로 실행해 위험했다
  • IE 8 · 9 는 XDomainRequest 라는 따로 된 API 를 썼다
