상태 코드는 응답의 첫 줄에 오는 세 자리 숫자로, 요청이 어떻게 됐는지 알린다. 첫 자리로 갈래가 정해진다 — 2 는 됨, 3 은 다른 곳으로, 4 는 요청 쪽 잘못, 5 는 서버 쪽 잘못이다. API 를 만들 때 알맞은 코드를 돌려주면, 브라우저 · 캐시 · 라이브러리 · 모니터링이 본문을 읽지 않고도 결과를 안다.

자주 쓰는 코드

코드 뜻 쓰는 때
200 OK 됐다 GET 결과 · 바꾼 결과
201 Created 만들었다 POST 로 새로 만듦 — Location 에 새 주소
204 No Content 됐고 본문이 없다 DELETE · 저장만 하는 PUT
301 Moved Permanently 영원히 옮겼다 주소를 바꿀 때 — 검색 엔진도 새 주소로 바꾼다
302 Found · 303 See Other 잠시 다른 곳으로 로그인 뒤 원래 쪽으로 · 폼 POST 뒤 결과 쪽으로
304 Not Modified 바뀐 것이 없다 캐시 확인 — 본문 없이
400 Bad Request 요청을 읽을 수 없다 JSON 문법 오류 · 빠진 헤더
401 Unauthorized 누구인지 모른다 로그인 안 함 · 토큰 만료
403 Forbidden 누구인지 알지만 안 된다 권한 없음
404 Not Found 없다 없는 주소 · 없는 id
409 Conflict 지금 상태와 부딪친다 이미 있는 이메일 · 다른 사람이 먼저 고침
422 Unprocessable Content 읽었지만 값이 틀렸다 입력 검사 실패
429 Too Many Requests 너무 많이 보냈다 요청 수 제한 — Retry-After
500 Internal Server Error 서버가 죽었다 처리하지 못한 예외
502 Bad Gateway · 503 Service Unavailable · 504 Gateway Timeout 앞단(Nginx · 로드 밸런서) 이 뒤의 서버에 닿지 못했다 배포 중 · 서버 다운 · 너무 느림

실제 응답

$ curl -i -X POST -H 'Content-Type: application/json' -d '{"title":"책"}' http://127.0.0.1:8801/api/todos
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Cookie realm="todo"
{"error":"로그인이 필요하다"}

$ curl -i -b jar -X POST -H 'Content-Type: application/json' -d '{}' http://127.0.0.1:8801/api/todos
HTTP/1.1 422 Unprocessable Entity
{"error":"title 이 비었다"}

$ curl -i http://127.0.0.1:8801/old
HTTP/1.1 301 Moved Permanently
Location: /api/todos

$ curl -sL -o /dev/null -w "%{http_code} %{url_effective} %{num_redirects}\n" http://127.0.0.1:8801/old
200 http://127.0.0.1:8801/api/todos 1             ← -L 은 Location 을 따라간다

$ curl -i http://127.0.0.1:8801/busy
HTTP/1.1 429 Too Many Requests
Retry-After: 30                                    ← 30 초 뒤에 다시
  • 이유 글자(Unprocessable Entity) 는 서버마다 다를 수 있고 HTTP/2 에는 아예 없다. 코드는 숫자로만 판단한다
  • 오류에도 본문에 무엇이 틀렸는지 적어 준다. 형식을 맞추려면 RFC 9457 의 application/problem+json(type · title · status · detail) 을 쓴다

헷갈리는 코드

  • 401 과 403: 로그인하면 될 일이면 401, 로그인해도 안 되면 403 이다. 있는지조차 숨겨야 하면 403 대신 404 를 준다
  • 400 과 422: 본문을 읽지도 못하면 400, 읽었는데 값이 규칙에 맞지 않으면 422 다
  • 301 · 302 와 307 · 308: 301 · 302 를 따라갈 때 브라우저는 POST 를 GET 으로 바꿔 버린다. 메서드와 본문을 그대로 두려면 307(잠시) · 308(영원히) 이다
  • 오류인데 200: 본문에 {"success": false} 를 담아 200 으로 주면 캐시 · 모니터링 · fetch 의 res.ok 가 성공으로 본다

브라우저 쪽에서

const res = await fetch("/api/todos");
res.ok;          // 200 ~ 299 면 true — fetch 는 404 · 500 에도 예외를 던지지 않는다
res.status;      // 404
res.redirected;  // 301 을 따라왔으면 true
  • 304 는 브라우저가 캐시에서 본문을 꺼내 200 으로 바꿔 준다. 스크립트는 304 를 보지 않는다

예전에는

  • 422 는 WebDAV 의 코드였고 이름이 Unprocessable Entity 였다. RFC 9110(2022) 에서 HTTP 표준이 되며 Unprocessable Content 가 됐다
  • 302 의 원래 뜻은 "메서드를 그대로" 였지만 브라우저가 GET 으로 바꿔 보내는 바람에, 뜻을 나눠 303 · 307 을 만들었다
