HTTP 는 요청마다 따로라서 서버는 앞의 요청을 기억하지 못한다. 서버가 응답에 Set-Cookie 로 작은 값을 주면 브라우저가 저장해 두었다가 같은 사이트로 가는 요청마다 Cookie 헤더로 돌려보내고, 서버는 그 값으로 누구인지 알아본다. 로그인은 보통 세션 id 를 쿠키에 넣고, 사용자 정보는 서버의 세션 저장소에 둔다.

로그인 흐름

sequenceDiagram
  participant B as 브라우저
  participant S as 서버
  B->>S: POST /login (아이디 · 비밀번호)
  Note over S: 세션 만들기 — sid → {user: "geon"}
  S-->>B: 200 · Set-Cookie: sid=7e51…; HttpOnly; SameSite=Lax; Max-Age=3600
  B->>S: GET /me · Cookie: sid=7e51…
  S-->>B: 200 {"user":"geon"}
  B->>S: POST /logout · Cookie: sid=7e51…
  Note over S: 세션 지우기
  S-->>B: 204 · Set-Cookie: sid=; Max-Age=0
$ curl -i -c jar -X POST http://127.0.0.1:8801/login          ← -c 는 받은 쿠키를 jar 에 저장
HTTP/1.1 200 OK
Set-Cookie: sid=7e51fd45cdfd624285318c8252ae1814; Path=/; HttpOnly; SameSite=Lax; Max-Age=3600

$ curl -b jar http://127.0.0.1:8801/me                        ← -b 는 jar 의 쿠키를 보낸다
{"user":"geon"}
$ curl -i http://127.0.0.1:8801/me
HTTP/1.1 401 Unauthorized
// Node — 세션 id 는 맞힐 수 없게 충분히 길고 무작위로
const sid = crypto.randomBytes(16).toString("hex");
sessions.set(sid, { user: "geon" });
res.setHeader("Set-Cookie", `sid=${sid}; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600`);

쿠키 속성

속성 뜻
HttpOnly 스크립트(document.cookie) 가 읽지 못한다 — XSS 로 훔쳐 가지 못하게
Secure https 로만 보낸다 (localhost 는 예외)
SameSite=Lax 다른 사이트에서 온 요청에는 보내지 않는다 — 링크를 눌러 들어오는 GET 만 보낸다 — Chrome 은 속성이 없으면 이것으로 본다
SameSite=Strict 다른 사이트에서 온 것은 링크라도 보내지 않는다
SameSite=None; Secure 다른 사이트에서도 보낸다 — 다른 사이트에 넣은 위젯 · 결제 창
Max-Age=3600 · Expires=… 살아 있는 시간 — 없으면 브라우저를 닫을 때 지워진다
Path=/ · Domain=example.com 보낼 경로 · 하위 도메인까지 보낼지
  • 로그인 쿠키는 HttpOnly; Secure; SameSite=Lax 를 기본으로 한다
  • 위 예에서 HttpOnly 쿠키는 document.cookie 가 "" 이고, fetch 응답의 res.headers.get("set-cookie") 도 null 이다. 스크립트는 로그인 쿠키를 만질 수 없다
  • 쿠키는 크기가 4KB 쯤이고 요청마다 따라간다. 화면 설정 같은 큰 값은 localStorage 에 둔다
  • 지우려면 같은 이름 · Path 로 Max-Age=0 을 보낸다

사이트와 출처

  • SameSite 의 "사이트" 는 출처보다 넓다. app.example.com 과 api.example.com 은 출처는 다르지만 같은 사이트라 Lax 쿠키가 간다
  • 포트도 사이트를 가르지 않는다. 위 예의 127.0.0.1:8802 에서 127.0.0.1:8801 로 간 요청에 쿠키가 실렸다(CORS 의 credentials 는 따로 필요하다)
  • 다른 사이트의 쿠키(서드파티 쿠키) 는 Safari 가 막고, Firefox 는 사이트마다 따로 담아 추적에 못 쓰게 한다. 광고 추적에 쓰였기 때문이다

세션 · 토큰

세션 쿠키 토큰 (JWT)
담는 것 무작위 id — 정보는 서버에 사용자 정보 + 서명
서버 세션 저장소(메모리 · Redis · DB) 를 찾는다 서명만 검사한다 — 저장소가 없다
로그아웃 · 강제 종료 세션을 지우면 끝 만료 전까지 막기 어렵다 — 짧게 주고 다시 받기
알맞은 곳 브라우저로 쓰는 웹 서비스 앱 · 서버끼리 · 여러 서비스가 함께 쓰는 로그인
  • 브라우저에서 토큰을 localStorage 에 두면 XSS 한 번에 털린다. 브라우저용이면 HttpOnly 쿠키에 넣는다
  • 로그인하면 세션 id 를 새로 만든다. 로그인 전 id 를 그대로 쓰면 남이 심어 둔 id 로 로그인될 수 있다(세션 고정)

CSRF

다른 사이트의 쪽이 내 사이트로 폼을 보내면, 브라우저가 내 쿠키를 붙여 보내 사용자 몰래 일이 처리될 수 있다.

  • SameSite=Lax 가 대부분 막는다. 다른 사이트에서 보낸 POST 에는 쿠키가 가지 않는다
  • 바꾸는 일은 GET 으로 하지 않는다. Lax 는 링크로 들어오는 GET 에는 쿠키를 보낸다
  • 더 막으려면 폼에 숨은 토큰(CSRF 토큰) 을 넣어 서버가 견준다. 프레임워크(Spring Security · Django) 가 해 준다

예전에는

  • SameSite 가 없어 모든 요청에 쿠키가 붙었고, CSRF 토큰이 꼭 필요했다. 2020 년 Chrome 이 Lax 를 기본으로 바꿨다
  • 세션 id 를 주소에 붙였다(;jsessionid=…). 주소가 공유 · 기록되며 새어 나가 지금은 쓰지 않는다
