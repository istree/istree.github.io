Spring Boot 앱은 바깥에 바로 내놓지 않고 앞에 Nginx 를 둔다. Nginx 가 80 · 443 과 HTTPS 를 받고, 앱은 127.0.0.1:8080 에서만 듣는다. 이때 앱이 보는 요청은 Nginx 가 보낸 것이라, 클라이언트 IP 와 https 를 알려면 Nginx 가 머리말(X-Forwarded-*) 을 붙이고 앱이 그것을 믿게 설정한다. 앱을 둘 띄워 Nginx 가 나눠 보내면, 하나씩 다시 띄워도 요청이 끊기지 않는다. 아래 예제는 Ubuntu 24.04 의 Nginx 1.24.0 과 systemd 로 띄운 Spring Boot 4.1.2 앱으로 돌렸다. 클라이언트는 같은 기계의 Docker 컨테이너(172.17.0.3) 다.

프록시

# /etc/nginx/sites-available/shop
server {
    listen 80;
    server_name shop.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
sudo ln -s /etc/nginx/sites-available/shop /etc/nginx/sites-enabled/shop
sudo nginx -t && sudo systemctl reload nginx
  • 앱은 server.address=127.0.0.1 로 띄우거나 방화벽으로 8080 을 막아, Nginx 를 거치지 않고는 닿지 않게 한다

클라이언트 IP 와 https

요청 정보를 돌려주는 /who 를 만들어, Nginx 가 TLS 를 받았다고 치고 X-Forwarded-Proto https 를 붙여 보냈다.

m.put("remoteAddr", r.getRemoteAddr());
m.put("scheme", r.getScheme());
m.put("link", ServletUriComponentsBuilder.fromCurrentContextPath().path("/orders/1").toUriString());
앱의 설정 remoteAddr scheme 앱이 만든 링크
(그대로) 127.0.0.1 http http://shop.example.com/orders/1
server.forward-headers-strategy=native 172.17.0.3 https https://shop.example.com/orders/1
  • 그대로 두면 앱은 모든 요청이 Nginx(127.0.0.1) 에서 http 로 온 줄 안다. 접속 기록 · IP 제한이 틀리고, 리다이렉트 · 링크가 http:// 로 나간다
  • native 는 Tomcat 이 머리말을 읽게 한다. 머리말을 믿는 것은 앞 주소가 내부 주소(127.0.0.1 · 10.x · 172.16 ~ 31.x · 192.168.x …) 일 때다. 그래서 같은 Docker 네트워크의 컨테이너가 Nginx 를 거치지 않고 앱(172.17.0.2:8080) 에 바로 X-Forwarded-For: 1.2.3.4 · X-Forwarded-Proto: https 를 보내자, 앱은 remoteAddr 를 1.2.3.4, scheme 을 https 로 그대로 믿었다. 앱 포트는 Nginx 만 닿게 막는다
  • 앱이 본 Host 는 Nginx 가 넘긴 것(proxy_set_header Host $host) 이다. 이 줄이 없으면 Nginx 는 proxy_pass 의 주소(127.0.0.1:8080) 를 Host 로 보낸다

앱이 꺼졌거나 느릴 때

상황 Nginx 의 답 error.log
앱을 멈춤 502 connect() failed (111: Connection refused) while connecting to upstream
5 초 걸리는 요청, proxy_read_timeout 3s 504, 3.0 초 upstream timed out (110: Connection timed out) while reading response header from upstream
  • proxy_read_timeout 의 기본은 60 초다. 오래 걸리는 내려받기 · 보고서 주소에만 따로 늘린다
  • 설정을 바꾸고 reload 한 직후의 요청 하나는 옛 설정으로 처리됐다(5 초 뒤 200). 새 설정을 시험할 때는 잠깐 뒤에 보낸다

Actuator 막기

location /actuator/ {
    allow 127.0.0.1;
    deny all;
    proxy_pass http://127.0.0.1:8080;
}
  • 같은 기계에서는 /actuator/health 가 200, 컨테이너(바깥) 에서 /actuator/prometheus 는 403 이었다
  • 지표는 Prometheus 만 읽으면 된다. Prometheus 가 다른 서버에 있으면 그 주소만 allow 하거나, 앱의 관리 포트를 따로 둔다(management.server.port=9090)

앱 둘을 번갈아 바꾸기

템플릿 유닛으로 앱을 8081 · 8082 에 띄우고 Nginx 가 나눠 보내게 했다.

upstream shop {
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
}
server {
    listen 80;
    server_name shop.example.com;
    location / {
        proxy_pass http://shop;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
sudo systemctl restart shop@8081     # 다 뜨기를 기다린 뒤
sudo systemctl restart shop@8082

0.05 초마다 요청을 보내면서 둘을 차례로 다시 띄웠다.

둘 사이 기다림 결과
첫째가 다 뜨자마자 둘째 200 82 · 502 68 — no live upstreams while connecting to upstream
첫째가 뜬 뒤 12 초 200 220 · 실패 0
  • 한 앱이 내려간 동안 Nginx 는 그 앱에 붙다 실패한 요청을 다른 앱으로 다시 보냈다(proxy_next_upstream error). 그래서 하나씩 내릴 때는 실패가 없다
  • 실패한 앱은 fail_timeout(기본 10 초) 동안 빼 둔다. 첫째가 다시 떴어도 Nginx 는 아직 빼 둔 상태라, 그 사이 둘째를 내리자 보낼 곳이 없어 502 가 났다. 둘째는 fail_timeout 이 지난 뒤에 내린다
  • 오픈 소스 Nginx 는 앱에 건강 검사를 따로 보내지 않는다. 실제 요청이 실패해야 빼고, 시간이 지나야 다시 넣는다
