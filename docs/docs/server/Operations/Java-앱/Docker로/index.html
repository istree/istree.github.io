Spring Boot 앱을 Docker 이미지로 만들면 JRE 와 jar 를 함께 옮겨, 서버에는 Docker 만 있으면 된다. Dockerfile 은 빌드 단계(JDK · Maven) 와 실행 단계(JRE) 를 나눠 이미지를 줄이고, jar 를 풀어 라이브러리와 내 코드를 다른 층에 넣어 코드만 바뀌었을 때 작은 층만 새로 만든다. 컨테이너에 메모리 한도를 주면 JVM 은 그 한도를 보고 힙을 정하므로, 비율로 정해 두면 한도를 바꿔도 맞춰진다. 아래 예제는 Spring Boot 4.1.2 앱을 maven:3.9-eclipse-temurin-25 에서 빌드하고 eclipse-temurin:25-jre(25.0.5, Ubuntu 26.04 바탕) 로 띄웠다.

Dockerfile

FROM maven:3.9-eclipse-temurin-25 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src src
RUN mvn -q -DskipTests package \
 && java -Djarmode=tools -jar target/shop-0.0.1-SNAPSHOT.jar extract --layers --launcher --destination /x

FROM eclipse-temurin:25-jre
RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/* \
 && useradd --system --uid 10001 shop
WORKDIR /app
COPY --from=build /x/dependencies/ ./
COPY --from=build /x/spring-boot-loader/ ./
COPY --from=build /x/snapshot-dependencies/ ./
COPY --from=build /x/application/ ./
USER shop
EXPOSE 8080
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
HEALTHCHECK --interval=5s --timeout=3s --start-period=20s CMD curl -fs localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
docker build -t shop:1 .
docker run -d --name shop -p 127.0.0.1:8080:8080 --memory 512m shop:1
  • pom.xml 만 먼저 넣고 라이브러리를 받아 두면(dependency:go-offline), 코드만 바뀐 빌드는 그 층을 다시 쓴다. 첫 빌드 46 초, 코드 한 줄을 바꾼 빌드 6 초였다
  • 실행 단계에는 JDK · Maven 이 없다. 이미지는 556 MB 였고, 그 가운데 내가 더한 층은 라이브러리 24.4 MB · 로더 696 kB · 내 코드 86 kB · curl 11.8 MB 다
  • eclipse-temurin:25-jre 에는 curl · wget 이 없다. 건강 검사를 curl 로 하려고 따로 깔았다
  • 이미지 안에서 root 로 돌지 않게 사용자를 만들어 USER 로 바꾼다. 컨테이너 안의 id 는 uid=10001(shop) 이었다

층 나누기

-Djarmode=tools … extract --layers 는 jar 를 네 폴더로 푼다.

application            80K     내 코드 · 설정
dependencies           24M     판이 정해진 라이브러리
snapshot-dependencies  4.0K    -SNAPSHOT 라이브러리
spring-boot-loader     676K    JarLauncher

코드만 바꿔 다시 빌드한 shop:2 와 shop:1 의 마지막 층 셋을 견줬다.

bfbcd3b8ea7b 5f70bf18a086 5926761dbc6f   ← shop:1
bfbcd3b8ea7b 5f70bf18a086 70a79ca85808   ← shop:2
  • 마지막 층(내 코드) 만 달라졌다. 서버가 새 이미지를 받을 때 86 kB 층 하나만 받는다
  • jar 를 통째로 COPY 하면 코드 한 줄을 바꿔도 24 MB 층을 다시 만들고 다시 받는다

메모리

--memory 512m 컨테이너에서 JVM 이 정한 최대 힙이다.

JVM 옵션 최대 힙
(없음) 134217728 — 128 MB, 한도의 25 %
-XX:MaxRAMPercentage=75 402653184 — 384 MB
-Xmx1g 1073741824 — 한도보다 크다

한도보다 큰 힙을 주면 어떻게 끝나는지 50 MB 씩 메모리를 잡는 프로그램으로 봤다.

JVM 옵션 끝
-Xmx1g 450 MB 에서 소리 없이 죽음 — 종료 코드 137 · OOMKilled=true
-XX:MaxRAMPercentage=75 java.lang.OutOfMemoryError — 종료 코드 1, 로그에 까닭이 남는다
  • -Xmx 를 한도보다 크게 주면 JVM 이 힙을 다 쓰기 전에 커널이 컨테이너를 죽인다. Java 의 오류 · 힙 덤프가 남지 않아 까닭을 찾기 어렵다
  • 비율로 정하면 한도를 바꿔도 힙이 따라간다. 힙 밖 메모리도 있으므로 75 % 를 넘기지 않는다
  • JAVA_TOOL_OPTIONS 는 JVM 이 스스로 읽는 환경 변수다. 로그 첫 줄에 Picked up JAVA_TOOL_OPTIONS: -XX:MaxRAMPercentage=75 가 나온다. docker run -e JAVA_TOOL_OPTIONS=… 로 바꿀 수 있다

건강 검사 · 끄기

docker inspect -f '{{.State.Health.Status}}' shop    # 띄우고 6 초 뒤 healthy
  • --start-period=20s 동안의 실패는 세지 않는다. 앱이 뜨는 데(3.4 초) 걸리는 시간보다 넉넉히 둔다
  • docker stop 은 SIGTERM 을 보내고 10 초 기다린 뒤 SIGKILL 이다. 5 초짜리 요청을 하는 중에 docker stop 하자 요청은 200 으로 끝났고, 컨테이너는 4 초 만에 종료 코드 143 으로 멈췄다
  • 셸을 거쳐 띄우면(ENTRYPOINT java … 꼴 · sh -c "java …") PID 1 이 sh 이고 Java 는 그 아래(PID 7) 다. SIGTERM 을 셸이 받고 Java 에 넘기지 않아, docker stop 이 10 초를 다 기다린 뒤 종료 코드 137 로 죽였다(graceful 로그 없음). 위처럼 JSON 배열 꼴로 쓴다
  • 앱의 graceful 기다림(30 초) 이 docker stop 의 10 초보다 길다. 오래 걸리는 요청이 있으면 docker stop -t 40 · compose 의 stop_grace_period: 40s 로 늘린다
