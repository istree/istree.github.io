Spring Boot 앱은 mvn package 로 실행 jar 하나를 만든다. jar 안에는 내 코드와 함께 라이브러리 jar 들과 내장 Tomcat 이 들어 있어 java -jar 하나로 뜬다. 설정은 jar 안의 application.yml 이 기본값이고, 서버에서는 환경 변수 · 명령줄 인자 · 바깥 파일로 덮어쓴다. 메모리는 JVM 옵션으로 정한다. 정하지 않으면 기계 메모리의 4 분의 1 이다. 끄라는 신호(SIGTERM) 를 받으면 하던 요청을 마치고 끝난다. 아래 예제는 start.spring.io 로 만든 Spring Boot 4.1.2 앱(web · actuator · prometheus) 을 maven:3.9-eclipse-temurin-25(JDK 25.0.4) 컨테이너에서 빌드 · 실행했다.

빌드

curl https://start.spring.io/starter.zip -d type=maven-project -d bootVersion=4.1.2 -d javaVersion=25 \
  -d groupId=demo -d artifactId=shop -d packageName=demo.shop \
  -d dependencies=web,actuator,prometheus -o shop.zip
mvn -DskipTests package
ls -la target/*.jar    # shop-0.0.1-SNAPSHOT.jar 24489053 바이트
  • 첫 빌드는 라이브러리를 받느라 25 초 걸렸다. ~/.m2 를 남겨 두면 다음부터 빨라진다
  • 4.x 에서 web 은 spring-boot-starter-webmvc 로 들어온다(3.x 는 spring-boot-starter-web)

jar 의 속은 이렇다.

jar tf target/shop-0.0.1-SNAPSHOT.jar | grep -c BOOT-INF/lib/    # 50
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: demo.shop.ShopApplication
Spring-Boot-Version: 4.1.2
Spring-Boot-Classes: BOOT-INF/classes/
Spring-Boot-Lib: BOOT-INF/lib/
  • 내 코드는 BOOT-INF/classes/, 라이브러리 jar 50 개(spring-boot-4.1.2.jar · tomcat-embed-core-11.0.27.jar …) 는 BOOT-INF/lib/ 에 있다. JarLauncher 가 이 둘로 클래스 경로를 꾸리고 Start-Class 를 부른다
  • 클래스 경로를 바꾸지 않고 jar 하나만 옮기면 되는 것이 서버에 올리기 쉬운 까닭이다

실행

java -jar target/shop-0.0.1-SNAPSHOT.jar
Starting ShopApplication v0.0.1-SNAPSHOT using Java 25.0.4.1 with PID 184
Tomcat started on port 8080 (http) with context path '/'
Started ShopApplication in 2.961 seconds (process running for 3.419)
curl localhost:8080/orders/1           # {"item":"apple","id":1}
curl localhost:8080/actuator/health    # {"groups":["liveness","readiness"],"status":"UP"}
  • 뜨는 데 3 초쯤이었다. 이 동안은 요청을 받지 못한다. 서비스를 다시 띄울 때 끊기는 시간이 이만큼이다
  • Actuator 는 health 만 처음부터 웹에 나온다. /actuator/env 는 404 였다. 내놓을 것은 설정으로 정한다
# src/main/resources/application.yml
server:
  port: 8080
  shutdown: graceful
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus

설정 덮어쓰기

jar 안의 server.port: 8080 을 여러 곳에서 덮어써 봤다.

준 것 뜬 포트
(그대로) 8080
SERVER_PORT=9090 9090
SERVER_PORT=9090 + -Dserver.port=9092 9092
SERVER_PORT=9090 + --server.port=9091 9091
실행한 폴더의 application.yml(port: 9093) 9093
실행한 폴더의 application.yml + SERVER_PORT=9090 9090
  • 명령줄 인자(--) > JVM 시스템 속성(-D) > 환경 변수 > 실행 폴더의 application.yml > jar 안의 application.yml 순서로 이겼다
  • 환경 변수 이름은 설정 이름을 대문자로 바꾸고 . 을 _ 로 바꾼 것이다(server.port → SERVER_PORT, spring.datasource.password → SPRING_DATASOURCE_PASSWORD). - 는 뺀다(server.forward-headers-strategy → SERVER_FORWARDHEADERSSTRATEGY). - 를 _ 로 바꾼 SERVER_FORWARD_HEADERS_STRATEGY 는 먹었지만, MANAGEMENT_METRICS_DISTRIBUTION_PERCENTILES_HISTOGRAM_HTTP_SERVER_REQUESTS=true 는 percentiles.histogram 으로 읽혀 Failed to bind properties under 'management.metrics.distribution.percentiles.histogram.http.server.requests' to double[] 로 앱이 뜨지 않았다. PERCENTILESHISTOGRAM 으로 붙여 쓰자 됐다
  • 서버마다 다른 값(DB 주소 · 비밀번호) 은 jar 에 넣지 않고 환경 변수로 준다. 같은 jar 를 개발 · 운영에 그대로 올린다
  • SPRING_PROFILES_ACTIVE=prod 를 주면 로그에 The following 1 profile is active: "prod" 가 나오고, application-prod.yml 을 더 읽는다

메모리

java -XX:+PrintFlagsFinal -version | grep -E " MaxHeapSize | MaxRAMPercentage "
   size_t MaxHeapSize      = 1025507328     {product} {ergonomic}
   double MaxRAMPercentage = 25.000000      {product} {default}
  • 힙을 정하지 않으면 기계 메모리의 25 % 다. 4 GB 가상 머신에서 1 GB 쯤이었다. 서버에 앱 하나만 돈다면 너무 작고, 여럿이면 합이 넘칠 수 있다
  • 서버에 바로 띄울 때는 -Xms256m -Xmx256m 처럼 정한다. 컨테이너에서는 -XX:MaxRAMPercentage=75 처럼 비율로 준다
  • 힙 밖에도 메모리를 쓴다(스레드 스택 · 메타스페이스 · 직접 버퍼). 힙 256 MB 로 띄운 앱의 프로세스 메모리가 244 MB 쯤이었다(아직 힙을 다 쓰지 않은 상태)

끄기

요청 하나가 5 초 걸리게 하고(?delay=5000), 1 초 뒤 SIGTERM 을 보냈다.

server.shutdown 그 요청 끝나기까지
graceful 200, 5.2 초 — 마치고 끝났다 5 초
immediate 빈 응답(curl: (52)) — 끊겼다 바로
정하지 않음(4.1 기본) 200 — graceful 로 돌았다 4 초 
o.s.boot.tomcat.GracefulShutdown : Commencing graceful shutdown. Waiting for active requests to complete
o.s.boot.tomcat.GracefulShutdown : Graceful shutdown complete
  • graceful 이어도 30 초(spring.lifecycle.timeout-per-shutdown-phase) 를 넘는 요청은 끊는다. 45 초짜리 요청은 31 초에 끊기고 Graceful shutdown aborted with one or more requests still active 가 남았다
  • SIGTERM 으로 끝난 Java 프로세스의 종료 코드는 143 이다. systemd 에 알려 줘야 정상 종료로 친다
  • kill -9(SIGKILL) 은 하던 요청을 모두 끊는다. 끄는 쪽(systemd · Docker) 의 기다림 시간을 30 초보다 길게 둔다
