Prometheus 의 경보는 규칙 파일에 PromQL 식을 적어 둔 것이다. Prometheus 가 정해진 간격으로 식을 계산해 결과가 나오면 경보가 pending 이 되고, 그 상태가 for 동안 이어지면 firing 이 되어 Alertmanager 로 보낸다. Alertmanager 는 받은 경보를 묶고(같은 경보 여럿을 한 번에), 점검 중인 것은 막고(silence), 정한 곳(메일 · 메신저 · webhook) 으로 보낸다. 문제가 풀리면 풀렸다는 알림(resolved) 도 보낸다. 아래 예제는 prom/prometheus:v3.13.5 · prom/alertmanager:v0.34.2 와, 받은 것을 찍기만 하는 작은 webhook 서버로 돌렸다. 앱은 Spring Boot 4.1.2 이고 요청의 5 % 가 500 이다.

규칙

# rules.yml
groups:
  - name: shop
    rules:
      - alert: ShopDown
        expr: up{job="shop"} == 0
        for: 30s
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 가 응답하지 않는다"
      - alert: ShopHighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{job="shop",status=~"5.."}[1m]))
            / sum(rate(http_server_requests_seconds_count{job="shop"}[1m])) > 0.03
        for: 1m
        labels:
          severity: warning
        annotations:
          summary: "오류율 {{ $value | humanizePercentage }}"
# prometheus.yml 에 더한다
global:
  evaluation_interval: 15s
rule_files:
  - /etc/prometheus/rules.yml
alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]
promtool check rules /etc/prometheus/rules.yml
curl -X POST localhost:9090/-/reload
  • for 는 잠깐 튀는 값으로 알리지 않으려고 둔다. 너무 길면 늦게 알린다
  • labels 는 Alertmanager 가 받는 곳을 나누는 데(severity), annotations 는 알림에 넣을 글에 쓴다. $labels · $value 로 값을 넣는다

Alertmanager

# alertmanager.yml
route:
  receiver: hook
  group_by: [alertname]
  group_wait: 10s
  group_interval: 1m
  repeat_interval: 4h
receivers:
  - name: hook
    webhook_configs:
      - url: http://hook:5001/
        send_resolved: true
docker run -d --name alertmanager --network mon -p 127.0.0.1:9093:9093 \
  -v $PWD/alertmanager.yml:/etc/alertmanager/alertmanager.yml prom/alertmanager:v0.34.2
amtool check-config /etc/alertmanager/alertmanager.yml     # SUCCESS
설정 뜻
group_by 이 라벨이 같은 경보를 한 알림으로 묶는다
group_wait 첫 경보를 받고 같은 묶음이 더 오기를 기다리는 시간
group_interval 묶음에 새 경보가 더해졌을 때(풀렸을 때) 다시 보내는 간격
repeat_interval 풀리지 않은 경보를 다시 알리는 간격
  • 받는 곳은 routes 로 나눈다(severity="critical" 은 전화 · 메신저, 나머지는 메일). Slack · 메일 · PagerDuty 는 따로 설정이 있고, 그 밖은 webhook 으로 받는다

경보가 오기까지

오류율 경보는 띄우고 15 초 뒤 pending, 1 분 뒤 firing 이 되어 왔다.

08:46:40 firing ShopHighErrorRate  오류율 4.198%

앱을 멈추고 ShopDown 이 오기까지를 쟀다.

앱을 멈추고 상태
0 ~ 16 초 inactive — 아직 다음 수집 전
21 초 pending — up 이 0
62 초 firing · webhook 에 옴 
08:48:15 firing ShopDown app:8080 app:8080 가 응답하지 않는다
  • 알림이 오기까지 = 다음 수집(많아야 15 초) + 규칙 계산(많아야 15 초) + for(30 초) + group_wait. 이 예에서 1 분쯤이었다
  • 앱이 멈추자 ShopHighErrorRate 는 inactive 로 바뀌었다. 지표가 없으면 식의 결과도 없어 경보가 풀린다. 오류율 경보만 두면 앱이 아예 죽었을 때 오히려 조용해진다. up == 0 경보를 함께 둔다
  • 앱을 다시 띄우자 61 초 뒤 resolved ShopDown 이 왔다. 풀린 알림은 group_interval(1 분) 에 맞춰 나간다

점검 중 막기

amtool --alertmanager.url=http://localhost:9093 silence add alertname=ShopDown \
  --duration=1h --comment="점검" --author=geon
amtool --alertmanager.url=http://localhost:9093 silence query
ID                                    Matchers              Ends At                  Created By  Comment
270ef8b3-1694-487b-917a-3f3a5c0a32a9  alertname="ShopDown"  2026-11-09 09:49:24 UTC  geon        점검
  • 막은 뒤 앱을 멈추자 Prometheus 에서는 ShopDown firing 이었지만 webhook 에는 오지 않았다. Alertmanager 에서는 amtool alert query --silenced 에 suppressed 로 보였다
  • 막기는 정한 시간이 지나면 저절로 풀린다. 끝없이 막아 두지 않는다
  • 한 경보가 다른 경보를 가리게 할 때는 inhibit_rules 를 쓴다(서버가 죽었으면 그 서버의 앱 경보는 보내지 않는다)

무엇에 경보를 걸까

경보 식
대상이 죽었다 up == 0 (for: 1m)
오류율이 높다 5xx 비율 > 0.05 (for: 5m)
느리다 p95 > 1 초 (for: 10m)
디스크가 곧 찬다 predict_linear(node_filesystem_avail_bytes[6h], 24 * 3600) < 0
인증서가 곧 끝난다 blackbox_exporter 의 probe_ssl_earliest_cert_expiry - time() < 14 * 86400
  • 사람이 바로 손써야 하는 것만 전화 · 메신저로 보낸다. 그 밖은 대시보드에서 본다. 쓸모없는 알림이 잦으면 진짜 알림도 넘기게 된다
