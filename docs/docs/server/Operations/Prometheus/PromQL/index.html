PromQL 은 Prometheus 에 쌓인 시계열을 묻는 말이다. 이름과 라벨로 시계열을 찾은 뒤, 함수로 바꾸고 연산자로 엮는다. 지표는 종류가 정해져 있다 — 늘기만 하는 counter(요청 수), 오르내리는 gauge(메모리), 값을 구간별로 센 histogram(응답 시간) 이다. counter 는 그대로 보면 쌓인 합이라 쓸모가 적고, rate 로 "초당 얼마" 로 바꿔 본다. histogram 은 histogram_quantile 로 백분위(p95) 를 구한다. 아래 예제는 prom/prometheus:v3.13.5 가 node_exporter 1.12.1 과 Spring Boot 4.1.2 앱(0.1 초마다 요청, 20 번에 하나 500 · 20 번에 하나 300 ms) 에서 모은 지표로 돌렸다.

시계열 선택

shop_orders_total                                   # 이름
http_server_requests_seconds_count{uri="/orders/{id}"}   # 라벨이 같다
http_server_requests_seconds_count{status=~"5.."}   # 정규식이 맞다 (!= · !~ 도 있다)
{job="shop"}                                        # 이름 없이 라벨만
shop_orders_total{instance="app:8080", job="shop"}  87
  • 결과는 시계열마다 한 값(즉시 벡터) 이다. 그 시각의 가장 최근 값이다
  • [1m] 을 붙이면 지난 1 분의 값들(범위 벡터) 이다. shop_orders_total[1m] 은 15 초 간격의 넷 37, 54, 71, 87 이었다. 그래프로 그리지 못하고 함수에 넣어 쓴다

counter 와 rate

rate(shop_orders_total[1m])            # 1.111111111111111 — 초당 주문 1.1 개
rate(shop_orders_total)                # 오류
parse error: expected type range vector in call to function "rate", got instant vector
  • rate 는 범위 안의 처음과 끝 값으로 초당 늘어난 양을 낸다. 1 분에 37 → 87 이면 대략 (87 − 37) / 45 초다
  • 앱을 다시 띄워 counter 가 0 으로 돌아가도 rate · increase 는 줄어든 것을 다시 센 것으로 보고 이어서 계산한다. 앱을 한 번 다시 띄운 뒤 resets(shop_orders_total[30m]) 은 1, 지금 값은 41 인데 increase(shop_orders_total[30m]) 은 310 이었다
  • 범위는 수집 간격의 네 배쯤으로 둔다(15 초 간격이면 [1m]). 너무 짧으면 점이 하나뿐이라 값이 나오지 않는다
  • increase(x[1h]) 는 그 시간 동안 늘어난 양이다(rate × 3600)

묶기

sum by (status) (rate(http_server_requests_seconds_count{uri="/orders/{id}"}[1m]))
{status="200"}  7.31111111111111
{status="500"}  0.39999999999999997
  • sum by (라벨) 은 그 라벨이 같은 것끼리 더하고 나머지 라벨을 버린다. sum without (instance) 는 거꾸로 그 라벨만 버린다
  • rate 를 먼저 하고 sum 은 뒤에 한다. sum 을 먼저 하면 앱 하나가 다시 떠 counter 가 줄어든 것을 rate 가 알아보지 못한다

오류율은 두 식을 나눈다.

sum(rate(http_server_requests_seconds_count{uri="/orders/{id}",status=~"5.."}[1m]))
  / sum(rate(http_server_requests_seconds_count{uri="/orders/{id}"}[1m]))
# 0.05187319884726225 — 5.2 %

histogram 과 백분위

histogram_quantile(0.5,  sum by (le) (rate(http_server_requests_seconds_bucket{uri="/orders/{id}"}[1m])))   # 0.0011 초
histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket{uri="/orders/{id}"}[1m])))   # 0.026 초
histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket{uri="/orders/{id}"}[1m])))   # 0.340 초
  • 요청의 5 % 가 300 ms 라, p95 는 그 경계(26 ms), p99 는 300 ms 쪽(340 ms) 에 걸렸다. 평균(_sum / _count) 은 16 ms 였다. 평균은 느린 요청을 가리므로 응답 시간은 p95 · p99 로 본다
  • _bucket 은 응답 시간이 le(이하) 인 요청 수의 counter 다. by (le) 를 꼭 남긴다. 버리면 histogram_quantile 이 구간을 모른다
  • 값은 구간 사이를 고르게 나눠 짐작한 것이다. 구간이 성기면 실제와 차이가 난다
  • 앱이 구간(_bucket) 을 내지 않으면 백분위를 구하지 못한다. Spring Boot 는 따로 켜야 한다

gauge

node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes                                  # 0.822 — 82 % 남음
node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}     # 0.930
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[1m])))                # 9.26 — CPU 9 %
count(node_cpu_seconds_total{mode="idle"})                                                   # 2 — 코어 수
  • gauge 는 그 값을 그대로 본다. rate 를 쓰지 않는다
  • CPU 는 counter(코어마다 모드별로 쓴 초) 라, 쉬는 시간(idle) 의 비율을 빼서 쓴 비율을 낸다
  • 두 지표를 나누면 라벨이 같은 것끼리 짝지어진다. 라벨이 어긋나면 결과가 비므로 on(…) · ignoring(…) 으로 맞출 라벨을 정한다

볼 것 식
대상이 죽었다 up == 0
초당 요청 수 sum(rate(http_server_requests_seconds_count[5m]))
오류율 sum(rate(…{status=~"5.."}[5m])) / sum(rate(…[5m]))
p95 응답 시간 histogram_quantile(0.95, sum by (le) (rate(…_bucket[5m])))
