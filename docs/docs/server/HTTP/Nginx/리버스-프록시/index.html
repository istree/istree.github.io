리버스 프록시

리버스 프록시는 바깥의 요청을 받아 안쪽 서버(Node · Java · Python 앱, GitLab · Jenkins 같은 도구) 로 넘기고 그 응답을 돌려주는 것이다. 앱은 127.0.0.1 의 포트에서만 돌고, Nginx 가 80 · 443 을 받아 HTTPS · 압축 · 정적 파일 · 여러 앱을 경로나 도메인으로 나누는 일을 맡는다. 아래 예제는 Ubuntu 24.04 의 nginx 1.24 뒤에, 받은 경로와 헤더를 그대로 돌려주는 파이썬 서버(3000 · 3001) 를 두고 돌렸다.

proxy_pass 끝의 /

location /a/ { proxy_pass http://127.0.0.1:3000; }        # 주소 뒤에 경로가 없다
location /b/ { proxy_pass http://127.0.0.1:3000/; }       # 경로 / 가 있다
location /c/ { proxy_pass http://127.0.0.1:3000/api/; }   # 경로 /api/ 가 있다
요청 앱이 받은 경로
/a/users?x=1 /a/users?x=1 — 그대로 넘긴다
/b/users?x=1 /users?x=1 — location 의 /b/ 를 / 로 바꾼다
/c/users /api/users — /c/ 를 /api/ 로 바꾼다
  • proxy_pass 에 경로(끝 / 하나라도) 가 있으면 location 에 맞은 부분을 그 경로로 바꾸고, 없으면 원래 경로를 그대로 넘긴다
  • 앱이 /gitlab 아래에서 돌게 설정되어 있으면 경로를 그대로 넘기는 /a/ 꼴(proxy_pass http://10.0.1.10:9021;) 을 쓴다. 앱이 / 에서 돌면 /b/ 꼴로 앞부분을 떼어 준다

헤더 넘기기

아무것도 정하지 않으면 앱은 Host: 127.0.0.1:3000 을 받고 누가 보냈는지 모른다.

location /h/ {
    proxy_pass http://127.0.0.1:3000/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
/a/users → {"path": "/a/users", "Host": "127.0.0.1:3000", "Connection": "close"}
/h/users → {"path": "/users", "Host": "p.test", "X-Real-IP": "127.0.0.1", "X-Forwarded-For": "10.0.0.9, 127.0.0.1", "X-Forwarded-Proto": "http", "Connection": "close"}
  • Host 를 넘겨야 앱이 만드는 주소(리다이렉트 · 링크) 가 바깥 도메인으로 나온다
  • X-Forwarded-For 는 앞에서 온 값(10.0.0.9) 에 지금 보낸 사람을 덧붙인다. 앱은 맨 앞 값을 그대로 믿지 말고, 믿을 수 있는 프록시가 붙인 값만 쓴다
  • X-Forwarded-Proto 로 앱이 원래 요청이 HTTPS 였는지 안다. 빠뜨리면 HTTPS 사이트에서 앱이 http:// 로 리다이렉트한다
  • Ubuntu 에는 이 네 줄이 /etc/nginx/proxy_params 에 들어 있어 include proxy_params; 한 줄로 쓴다 (Host 는 $http_host)

WebSocket

location /ws/ {
    proxy_pass http://127.0.0.1:3000/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
/ws/chat → {"path": "/chat", "Upgrade": "websocket", "Connection": "upgrade"}
  • Nginx 는 Upgrade · Connection 을 넘기지 않는다. 이 세 줄이 없으면 앱이 WebSocket 요청인 줄 모른다
  • 연결이 오래 조용하면 proxy_read_timeout(기본 60 초) 에 끊긴다. 채팅처럼 오래 열어 두면 늘리거나 앱이 핑을 보낸다

여러 앱으로 나누기 (upstream)

upstream app {
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
}
location /lb/ { proxy_pass http://app/; }
/lb/ → app1
/lb/ → app2
/lb/ → app1
/lb/ → app2
  • 기본은 차례로 나눈다(라운드 로빈). least_conn; 은 연결이 적은 쪽, ip_hash; 는 같은 사용자를 같은 서버로 보낸다
  • 서버 하나가 죽으면 그 서버를 잠시(기본 10 초) 빼고 다른 쪽으로 보낸다. 3001 을 끄고 네 번 부르면 모두 200 이었고, 오류 로그에는 Connection refused 가 한 번만 남았다
  • upstream 이름을 쓰면 앱이 받는 Host 가 app 이 된다. 위의 proxy_set_header Host $host; 를 함께 둔다

시간 제한 · 크기 제한

location /slow/ { proxy_pass http://127.0.0.1:3000/slow/; proxy_read_timeout 2s; }   # 5 초 걸리는 앱
location /up2/  { proxy_pass http://127.0.0.1:3000/; client_max_body_size 20M; }
경우 응답 오류 로그
앱이 꺼져 있다 502 connect() failed (111: Connection refused) while connecting to upstream
앱이 늦다 (2 초 제한, 5 초 걸림) 504 (2.0 초) upstream timed out (110: Connection timed out) while reading response header from upstream
2 MB 를 올렸다 (기본 1 MB) 413 client intended to send too large body: 2000000 bytes
2 MB, client_max_body_size 20M 200 —
  • 502 는 앱이 죽었거나 포트가 틀린 것, 504 는 앱이 살아 있지만 늦은 것이다. 먼저 curl 127.0.0.1:3000 으로 앱을 직접 불러 본다
  • 파일을 올리는 앱(GitLab · Nexus · 그림 올리기) 은 client_max_body_size 를 server 나 location 에 늘린다. 0 이면 제한이 없다
