Redis 를 캐시로 쓸 때는 대개 cache-aside 다. 앱이 먼저 Redis 에서 찾고, 없으면 DB 에서 읽어 Redis 에 TTL 과 함께 넣는다. 자료를 고치면 캐시 키를 지운다. 이때 두 가지를 정해 둔다. 하나는 메모리가 찼을 때 무엇을 쫓아낼지(maxmemory-policy) 다. 다른 하나는 인기 키가 만료되는 순간 많은 요청이 한꺼번에 DB 로 몰리는 캐시 스탬피드를 어떻게 막을지다. 아래 예제는 redis:8(8.10.3) 컨테이너에, 같은 네트워크의 Python 3.13 · redis 8.1.0 으로 붙어 돌렸다. DB 는 0.1 초 걸리는 함수로 흉내 냈다.

cache-aside

import json, redis
r = redis.Redis(host="redis", decode_responses=True)

def get_user(uid):
    key = f"user:{uid}"
    v = r.get(key)
    if v is not None:
        return json.loads(v)              # 캐시에 있다
    u = db_load(uid)                      # 없으면 DB 에서
    r.set(key, json.dumps(u), ex=3600)    # TTL 1 시간
    return u

def update_user(uid, name):
    db_update(uid, name)
    r.delete(f"user:{uid}")               # 고친 뒤 캐시를 지운다
  • 첫 요청은 102 ms(DB), 둘째 요청은 0.2 ms(Redis) 였다
  • 고칠 때 캐시에 새 값을 넣지 않고 지운다. 두 요청이 거의 함께 고치면 넣는 순서가 뒤바뀌어 옛 값이 남을 수 있다. 지우면 다음 읽기가 DB 에서 새로 채운다
  • TTL 은 꼭 준다. 지우기를 빠뜨린 곳이 있어도 TTL 이 지나면 맞는 값으로 돌아온다
  • 맞힌 비율은 INFO stats 의 keyspace_hits · keyspace_misses 로 본다(hits / (hits + misses)). 모니터링에 이 둘과 evicted_keys 를 넣는다

키 이름

형태 예
종류:id user:42
앱:종류:id shop:user:42 — 한 Redis 를 여러 앱이 쓸 때
…:v2 shop:user:42:v2 — 담는 JSON 의 형식을 바꿀 때
lock:키 lock:user:42 — 그 키를 채우는 중이라는 표시
  • JSON 형식을 바꿀 때 판을 키에 붙이면, 옛 앱과 새 앱이 함께 도는 동안 서로의 값을 읽지 않는다. 옛 키는 TTL 로 사라진다
  • ACL 의 ~shop:* · --scan --pattern 'shop:*' 이 앞붙이로 묶는다

메모리 한도

캐시로 쓰는 Redis 에는 한도와 쫓아내는 정책을 정한다. 한도가 없으면(기본 maxmemory 0) 서버의 메모리를 다 쓸 때까지 늘어난다.

maxmemory 256mb
maxmemory-policy allkeys-lru

한도 10 MB 에 TTL 있는 키 5000 개를 넣고, TTL 없는 키를 10 만 개까지 넣어 봤다(값 100 바이트).

정책 결과
noeviction (기본) 51069 개째에 OOM command not allowed when used memory > 'maxmemory'. — 앱의 쓰기가 오류가 된다
allkeys-lru 10 만 개가 다 들어가고, 오래 안 쓴 키 49972 개를 쫓아냈다. 처음 넣은 k:0 · TTL 키 t:0 이 모두 사라졌다
volatile-ttl TTL 있는 키를 남은 시간 짧은 순으로 4178 개 쫓아낸 뒤 55376 개째에 OOM — TTL 없는 키는 건드리지 않는다
volatile-lru TTL 있는 키 가운데 오래 안 쓴 것을 쫓아낸 뒤 OOM
  • 캐시만 담는 Redis 는 allkeys-lru 를 쓴다. 쫓겨난 키는 다음 읽기에 DB 에서 다시 채워진다
  • 캐시와 지워지면 안 되는 자료(세션 · 큐) 를 한 Redis 에 둔다면 volatile-* 로 캐시에만 TTL 을 준다. 다만 TTL 키가 바닥나면 OOM 이다. 나눌 수 있으면 Redis 를 나눈다
  • INFO memory 의 used_memory_human 이 한도(maxmemory_human) 에 붙어 있고 evicted_keys 가 늘면 한도가 작은 것이다

캐시 스탬피드

인기 키가 없거나 만료되면, 그 순간 들어온 요청이 모두 DB 로 간다. 키 하나에 200 요청을 한꺼번에 보냈다.

방법 DB 읽기
그대로 (위 cache-aside) 200 번, 200 개가 동시에
잠금 키 2 번
잠금 키 + 잡은 뒤 다시 보기 1 번

한 요청만 DB 에서 읽게 하고, 나머지는 잠깐 기다렸다 캐시를 다시 본다.

import time

def get_user(uid):
    key = f"user:{uid}"
    while True:
        v = r.get(key)
        if v is not None:
            return json.loads(v)
        if r.set(f"lock:{key}", "1", nx=True, ex=5):      # 잠금을 잡은 하나만
            try:
                v = r.get(key)                             # 잡는 사이 남이 채웠는지
                if v is not None:
                    return json.loads(v)
                u = db_load(uid)
                r.set(key, json.dumps(u), ex=3600)
                return u
            finally:
                r.delete(f"lock:{key}")
        time.sleep(0.02)                                   # 못 잡았으면 잠깐 뒤 다시
  • 잡은 뒤 다시 보지 않으면 2 번이었다. 캐시가 빈 것을 본 요청이, 앞 요청이 채우고 잠금을 푼 뒤에 잠금을 잡아 한 번 더 읽었다
  • 잠금의 ex=5 는 DB 읽기가 걸릴 시간보다 길게 준다. 잡은 프로세스가 죽어도 5 초 뒤 풀린다

확률적 조기 만료

만료되기 전에 미리 새로 읽으면, 기다리는 요청이 없다. 만료가 가까울수록 높은 확률로 한 요청이 먼저 다시 읽는다(XFetch). 값과 함께 DB 읽기에 걸린 시간(delta) · 만료 시각을 둔다.

import math, random

def get_user(uid, ttl=3600, beta=1.0):
    key = f"user:{uid}"
    h = r.hgetall(key)
    if h:
        delta, expiry = float(h["delta"]), float(h["expiry"])
        early = -delta * beta * math.log(random.random())  # 0 근처가 많고 가끔 크다
        if time.time() + early < expiry:
            return json.loads(h["v"])                      # 아직 새로 읽지 않는다
        if not r.set(f"lock:{key}", "1", nx=True, ex=5):
            return json.loads(h["v"])                      # 남이 새로 읽는 중 — 옛 값을 준다
    t0 = time.time()
    u = db_load(uid)
    delta = time.time() - t0
    p = r.pipeline()
    p.hset(key, mapping={"v": json.dumps(u), "delta": delta, "expiry": time.time() + ttl})
    p.expire(key, ttl)
    p.delete(f"lock:{key}")
    p.execute()
    return u

TTL 2 초짜리 키에 20 개가 6 초 동안 쉬지 않고 요청했다(캐시를 채운 뒤부터 셈).

방법 DB 읽기 동시에 가장 많이 느린 응답
그대로 40 번 20 40
조기 만료만 6 · 12 번 4 · 7 6 · 12
조기 만료 + 잠금 3 · 4 번 1 3 · 4
  • 그대로 두면 2 초마다 20 개가 모두 비어 있는 캐시를 보고 DB 로 갔다
  • 조기 만료만 쓰면 만료 직전에 여러 요청이 함께 "이제 새로 읽자" 로 뽑혀 DB 읽기가 겹쳤다. 요청이 많을수록 겹친다. 잠금을 더하자 새로 읽는 요청이 늘 하나였다
  • 다시 읽은 요청 하나만 느리고, 나머지는 만료 전의 값을 바로 받았다. 아주 잠깐 옛 값을 줘도 되는 자료에 쓴다
  • beta 를 키우면 더 일찍 새로 읽는다. 키가 처음 비어 있을 때(서버를 막 띄웠을 때) 는 조기 만료가 소용없어 위의 잠금 키 방식이 함께 필요하다
