Cassandra 클러스터는 노드들이 토큰 범위를 나눠 가진 링이다. 복제 계수가 3 이면 한 파티션을 노드 셋이 저마다 가진다. 주인 노드가 없어 앱은 아무 노드에나 붙고, 그 노드(코디네이터) 가 자료를 가진 노드들에 요청을 나른다. 요청마다 일관성 수준으로 "몇 노드가 답해야 성공인가" 를 정한다. ONE 은 노드가 하나만 살아 있어도 되는 대신 옛 값을 읽을 수 있고, QUORUM 은 과반이 살아 있어야 하는 대신 쓰기와 읽기가 겹쳐 방금 쓴 값을 읽는다. MongoDB 의 복제 세트가 과반을 잃으면 쓰기를 멈추는 것과 달리, Cassandra 는 이 선택을 요청마다 앱에 맡긴다. 아래 예제는 cassandra:5(5.0.9) 노드 셋(c1 · c2 · c3) 을 한 Docker 네트워크에 띄워 돌렸다.

노드 더하기

docker run -d --name c2 --hostname c2 --network cass-net \
  -e MAX_HEAP_SIZE=768M -e CASSANDRA_CLUSTER_NAME=shop -e CASSANDRA_DC=dc1 \
  -e CASSANDRA_ENDPOINT_SNITCH=GossipingPropertyFileSnitch \
  -e CASSANDRA_SEEDS=c1 \
  -v c2-data:/var/lib/cassandra cassandra:5
# nodetool status 에 UN 이 둘이 된 뒤 c3 을 같은 식으로
  • CASSANDRA_SEEDS 는 처음 찾아갈 노드다. 붙은 뒤에는 노드끼리 서로의 상태를 퍼뜨린다(gossip). 운영에서는 DC 마다 두셋을 seed 로 적는다
  • 노드는 하나씩 붙인다. c2 · c3 모두 UN 이 되기까지 67 · 69 초 걸렸다
  • 노드가 붙으면 토큰 범위를 나눠 받는다. 노드마다 토큰 16 개(num_tokens: 16) 를 링의 여러 곳에 둔다

복제 계수

ALTER KEYSPACE shop WITH replication = {'class': 'NetworkTopologyStrategy', 'dc1': 3};
-- Warnings : When increasing replication factor you need to run a full (-full) repair to distribute the data.
CREATE TABLE shop.kv (k int PRIMARY KEY, v text);
nodetool getendpoints shop kv 1    # 172.19.0.4 · 172.19.0.2 · 172.19.0.3 — 셋 다 가진다
  • 복제 계수를 올려도 있던 자료는 저절로 옮겨지지 않는다. 경고대로 nodetool repair -full shop 을 돌린다
  • 복제 계수는 노드 수보다 클 수 없고, 운영은 DC 마다 3 이 보통이다. 그래야 QUORUM(둘) 이 노드 하나를 잃고도 된다

일관성 수준

수준 답해야 하는 노드 (복제 계수 3)
ONE 1
QUORUM 2
ALL 3
LOCAL_QUORUM 이 DC 의 과반 — DC 가 여럿일 때

cqlsh 에서 CONSISTENCY … 를 바꿔 가며 노드를 껐다.

살아 있는 노드 ONE QUORUM ALL
셋 된다 된다 된다
둘 (c3 끔) 된다 된다 Cannot achieve consistency level ALL
하나 (c2 · c3 끔) 된다 Cannot achieve consistency level QUORUM — 
NoHostAvailable: ('Unable to complete the operation against any hosts', {<Host: 127.0.0.1:9042 dc1>:
  Unavailable('Error from server: code=1000 [Unavailable exception] message="Cannot achieve consistency level QUORUM"
  info={\'consistency\': \'QUORUM\', \'required_replicas\': 2, \'alive_replicas\': 1}')})
  • 노드 하나만 남아도 ONE 으로는 읽고 썼다. 같은 상황에서 MongoDB 의 복제 세트는 primary 가 없어 쓰기를 받지 않는다
  • 쓰기 QUORUM 과 읽기 QUORUM 은 셋 중 둘씩이라 적어도 한 노드가 겹친다. 그래서 방금 쓴 값을 읽는다. 쓰기 ONE · 읽기 ONE 은 겹치지 않을 수 있다(아래)

옛 값 읽기

c2 · c3 를 끈 채 c1 에서 ONE 으로 k = 1 을 old 에서 new 로 바꾸고, 자료가 없던 k = 7 을 넣었다. 그리고 두 노드를 다시 띄웠다. 늦게 온 노드에 쓰기를 전해 주는 힌트는 시험을 위해 꺼 뒀다(nodetool disablehandoff).

c3 에 붙어 읽기 결과
ONE 으로 k = 1 세 번 new · old · old
ONE 으로 k = 7 없음
QUORUM 으로 k = 1 new
nodetool repair -full shop(5 초) 뒤 ONE 세 번 new · new · new, k = 7 도 나왔다
  • ONE 은 코디네이터가 고른 노드 하나의 값이다. 그 노드가 그 쓰기를 받지 못했으면 옛 값이 온다
  • QUORUM 읽기는 두 노드의 값 가운데 쓴 시각이 늦은 것을 돌려주고, 늦은 노드를 고쳐 둔다(read repair)
  • 꺼진 노드가 힌트 시간(max_hint_window: 3h) 보다 오래 꺼져 있었거나 힌트를 놓쳤으면 repair 로만 맞춰진다. 운영에서는 표의 gc_grace_seconds(기본 864000, 10 일) 안에 모든 노드를 한 번씩 repair 한다 — Reaper 같은 도구로 예약한다

힌트

힌트를 켠 채(기본) c3 을 끄고 ONE 으로 k = 8 을 썼다. c3 을 다시 띄우자 c1 의 로그에 이 줄이 나왔다.

Finished hinted handoff of file e713c9c1-…-1794200421679-2.hints to endpoint /172.19.0.4:7000
  • 코디네이터는 꺼진 노드 몫의 쓰기를 힌트로 들고 있다가, 그 노드가 돌아오면 건네준다. 짧게 꺼졌다 켜진 노드는 이것으로 따라잡는다
  • 힌트는 쓰기를 성공으로 셈하지 않는다. QUORUM 쓰기에 노드가 하나만 살아 있으면 힌트가 있어도 실패다

노드 빼기

할 일 명령 결과
죽은 노드를 뺀다 다른 노드에서 nodetool removenode <Host ID> 꺼 둔 c3 를 34 초 만에 뺐다. 그 노드 몫의 자료는 남은 노드끼리 다시 맞춘다
살아 있는 노드를 뺀다 그 노드에서 nodetool decommission 노드 둘에서 c2 를 빼려 하자 거부했다 
nodetool: Unsupported operation: Not enough live nodes to maintain replication factor in keyspace system_distributed (RF = 3, N = 2). Perform a forceful decommission to ignore.
  • 노드를 빼면 복제 계수만큼의 노드가 남아야 한다. 복제 계수 3 이면 노드 셋 아래로 줄이기 전에 키스페이스의 복제 계수부터 낮춘다
  • nodetool status 의 Host ID 로 노드를 가리킨다. IP 는 다시 쓰일 수 있다
