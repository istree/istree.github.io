복제 세트는 같은 자료를 가진 mongod 여럿의 묶음이다. 쓰기는 primary 하나가 받고, secondary 들이 그 기록(oplog) 을 받아 따라 쓴다. primary 가 죽으면 남은 노드가 투표해 새 primary 를 뽑는다. 투표는 과반이 있어야 이기므로 노드는 셋 이상 홀수로 둔다. 셋이면 하나가 죽어도 쓰기가 이어지고, 둘이 죽으면 남은 하나는 primary 가 되지 못해 쓰기가 멈춘다. 이것이 분산 DB 가 장애 때 고르는 길이다 — 자료가 엇갈리느니(일관성) 쓰기를 멈춘다(가용성). 아래 예제는 mongo:9(9.0.4) 컨테이너 셋(mongo1 · mongo2 · mongo3) 을 한 Docker 네트워크에 띄워 돌렸다.

띄우기

노드끼리도 서로 인증해야 한다. 같은 열쇠 파일을 모든 노드에 나눠 준다.

# 열쇠 파일을 볼륨에 만든다 — 주인은 컨테이너의 mongodb(uid 999), 권한 400
docker run --rm -v mongo-key:/key mongo:9 bash -c \
  'openssl rand -base64 756 > /key/keyfile && chmod 400 /key/keyfile && chown 999:999 /key/keyfile'

for i in 1 2 3; do
  docker run -d --name mongo$i --hostname mongo$i --network mongo-net \
    -v mongo-key:/key:ro -v mongo$i-data:/data/db \
    mongo:9 mongod --replSet rs0 --bind_ip_all --keyFile /key/keyfile
done
// mongo1 에서 (아직 사용자가 없어 localhost exception 으로 들어간다)
rs.initiate({ _id: "rs0", members: [
  { _id: 0, host: "mongo1:27017" },
  { _id: 1, host: "mongo2:27017" },
  { _id: 2, host: "mongo3:27017" },
]})
// 10 초쯤 뒤 primary 가 정해지면
db.getSiblingDB("admin").createUser({ user: "root", pwd: "Root-pass-1", roles: ["root"] })
rs.status().members.map(m => m.name + " " + m.stateStr)
// [ 'mongo1:27017 PRIMARY', 'mongo2:27017 SECONDARY', 'mongo3:27017 SECONDARY' ]
  • host 에는 앱도 찾을 수 있는 이름을 적는다. 드라이버는 이 이름으로 노드마다 다시 붙는다
  • --keyFile 을 주면 인증도 함께 켜진다

붙기

mongodb://root:Root-pass-1@mongo1:27017,mongo2:27017,mongo3:27017/?replicaSet=rs0&authSource=admin
  • 노드를 모두 적고 replicaSet 을 준다. 드라이버가 지금의 primary 를 찾아 쓰고, 바뀌면 따라간다(db.hello().primary → mongo1:27017)
  • 노드 하나에만 바로 붙어(directConnection=true) secondary 에 쓰면 MongoServerError: not primary 다

쓰기 확인

writeConcern 성공을 돌려주는 때
w: 1 primary 가 썼을 때
w: "majority" (5.0 부터 기본) 과반(셋 중 둘) 이 썼을 때
  • 기본값은 db.adminCommand({ getDefaultRWConcern: 1 }) 로 본다 — { w: 'majority', wtimeout: 0 }
  • w: 1 로 성공한 쓰기는 primary 가 그 직후 죽으면 사라질 수 있다. 새 primary 가 그 쓰기를 받기 전이라면, 옛 primary 가 돌아올 때 그 쓰기를 되돌린다(rollback). majority 로 성공한 쓰기는 남는다

primary 를 꺼 보기

0.1 초마다 w: "majority" 로 하나씩 넣으면서 primary 를 껐다.

끄는 법 앱에서 본 것
docker stop mongo1 (SIGTERM) 오류 없이 바로 mongo2 가 primary. 끄기 전에 primary 를 넘겨주고(step down) 내려간다
docker kill mongo2 (SIGKILL) 쓰기 하나가 10.2 초 기다린 뒤 성공하고, mongo3 이 primary. 400 개가 모두 들어갔다 
"msg":"Starting an election, since we've seen no PRIMARY in election timeout period"
"msg":"Election succeeded, assuming primary role"
"msg":"Transition to primary complete; database writes are now permitted"
  • 갑자기 죽으면 남은 노드는 electionTimeoutMillis(기본 10000) 동안 primary 소리를 못 들은 뒤 선거를 한다. 그동안 쓰기는 멈춘다
  • 드라이버는 실패한 쓰기를 한 번 다시 보낸다(retryable writes). 그래서 앱에는 오류가 아니라 10 초쯤 걸린 쓰기로 보였다. 앱의 요청 시간 제한이 10 초보다 짧으면 그쪽에서 실패한다
  • 죽었던 노드를 다시 띄우면 secondary 로 돌아와 그 사이의 기록을 따라잡는다

둘을 꺼 보기

mongo3 을 죽인 채 primary(mongo1) 도 죽였다. 남은 mongo2 는 이렇다.

db.hello().isWritablePrimary   // false
rs.status().members.map(m => m.name + " " + m.stateStr)
// [ 'mongo1:27017 (not reachable/healthy)', 'mongo2:27017 SECONDARY', 'mongo3:27017 (not reachable/healthy)' ]
요청 결과
쓰기 MongoServerSelectionError — primary 가 없다
readPreference=secondaryPreferred 로 읽기 400 — 읽기는 된다
  • 셋 중 하나만 남으면 과반(둘) 이 안 되어 스스로 primary 가 되지 않는다. 네트워크가 둘로 갈렸을 때 양쪽이 각자 primary 가 되어 자료가 엇갈리는 것을 막는 규칙이다
  • 죽인 두 노드를 다시 띄우자 primary 가 뽑히고(mongo2) 쓰기가 이어졌다

읽기 선호

readPreference 읽는 곳
primary (기본) primary 만
primaryPreferred primary, 없으면 secondary
secondary secondary 만
secondaryPreferred secondary, 없으면 primary
nearest 가장 빨리 답하는 노드
  • secondary 는 primary 보다 조금 늦다. 방금 쓴 것을 바로 읽어야 하는 화면(쓰고 나서 목록 보기) 은 primary 로 읽는다
  • 보고서 · 백업처럼 늦어도 되는 무거운 읽기를 secondary 로 보내 primary 의 짐을 던다

노드 둘이면

노드 둘(primary + secondary) 은 하나가 죽으면 남은 하나가 과반이 아니어서 쓰기가 멈춘다. 노드 하나일 때보다 나을 게 없다. 셋째 서버를 둘 수 없으면 자료 없이 투표만 하는 arbiter 를 더한다. 다만 arbiter 가 있는 셋에서 자료 노드 하나가 죽으면 w: "majority" 쓰기가 끝나지 않으므로, 자료 노드 셋이 낫다.
