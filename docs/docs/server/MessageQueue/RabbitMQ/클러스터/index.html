RabbitMQ 클러스터는 노드 여럿이 사용자 · vhost · 교환기 · 큐 정의를 함께 갖는 묶음이다. 다만 큐의 메시지는 큐 종류에 따라 다르게 놓인다. classic 큐는 만든 노드 하나에만 있어, 그 노드가 죽으면 다른 노드에 붙어도 쓰지 못한다. quorum 큐는 노드 셋(이상) 에 복제되고, 그중 하나(리더) 가 받아 과반이 쓰면 확인한다. 리더 노드가 죽으면 남은 노드가 새 리더를 뽑는다. 4.0 부터 옛 미러링 큐(classic mirrored) 가 없어져, 복제가 필요하면 quorum 큐를 쓴다. 노드끼리는 같은 Erlang 쿠키로 서로를 믿는다. 아래 예제는 rabbitmq:4.4-management(4.4.0) 노드 셋(r1 · r2 · r3) 과 Java 클라이언트(amqp-client 5.37.1) 로 돌렸다.

묶기

노드마다 같은 쿠키를 /var/lib/rabbitmq/.erlang.cookie(주인 rabbitmq, 권한 400) 에 둔다.

# 쿠키 하나를 볼륨에 만들고, 노드가 뜰 때 제자리에 복사한다
docker run --rm -v mq-cookie:/c alpine:3.22 sh -c \
  'head -c 32 /dev/urandom | base64 | tr -dc A-Za-z0-9 > /c/.erlang.cookie; chmod 400 /c/.erlang.cookie; chown 999:999 /c/.erlang.cookie'

for i in 1 2 3; do
  docker run -d --name r$i --hostname r$i --network mq-net \
    -v mq-cookie:/cookie:ro -v r$i-data:/var/lib/rabbitmq \
    -e RABBITMQ_DEFAULT_USER=admin -e RABBITMQ_DEFAULT_PASS=Admin-pass-1 \
    rabbitmq:4.4-management bash -c \
    'cp /cookie/.erlang.cookie /var/lib/rabbitmq/ && chown rabbitmq:rabbitmq /var/lib/rabbitmq/.erlang.cookie \
     && chmod 400 /var/lib/rabbitmq/.erlang.cookie && exec docker-entrypoint.sh rabbitmq-server'
done
# r2 · r3 에서
rabbitmqctl stop_app
rabbitmqctl join_cluster rabbit@r1     # Clustering node rabbit@r2 with rabbit@r1
rabbitmqctl start_app

rabbitmqctl cluster_status             # Running Nodes: rabbit@r1 · rabbit@r2 · rabbit@r3
  • 붙은 노드는 제 사용자 · 큐를 버리고 클러스터의 것을 받는다. r3 에서 list_users 를 하자 admin 하나였다
  • 쿠키가 다른 노드 r4 로 join_cluster 하자 실패했고, r1 의 로그에 ** Connection attempt from node rabbit@r4 rejected. Invalid challenge reply. ** 가 남았다
  • 노드 이름은 rabbit@호스트 이름 이다. 호스트 이름이 바뀌면 다른 노드가 된다
  • 노드 수는 홀수(셋 · 다섯) 로 둔다. quorum 큐가 과반으로 움직이기 때문이다

quorum 큐

ch.queueDeclare("q.orders", true, false, false, Map.of("x-queue-type", "quorum"));
rabbitmqctl list_queues name type leader members
q.orders	quorum	rabbit@r2	[rabbit@r2, rabbit@r1, rabbit@r3]
q.classic	classic	rabbit@r2	[rabbit@r2]
  • 노드 셋에 복제됐다(members). 복제 수의 기본은 서버 설정 quorum_cluster_size 3 이라 노드가 더 많아도 셋에 두고, 큐마다 x-quorum-initial-group-size 로 바꾼다
  • 메시지는 persistent 로 보내지 않아도 디스크에 남는다
  • 미러링 큐는 rabbitmq-diagnostics list_deprecated_features 에서 classic_queue_mirroring · removed 다

노드를 꺼 보기

0.1 초마다 confirm 을 기다리며 q.orders 에 보내는 프로듀서를 띄웠다. 클라이언트에 노드 셋을 모두 주고 자동 복구를 켰다.

var f = new ConnectionFactory();
f.setAutomaticRecoveryEnabled(true);        // 기본도 켜짐
f.setNetworkRecoveryInterval(1000);
f.setConnectionTimeout(3000);               // 아래
Connection c = f.newConnection(Address.parseAddresses("r1:5672,r2:5672,r3:5672"));
끈 노드 결과
리더 노드(r2), 클라이언트는 다른 노드에 붙어 있음 280 건 모두 확인 · 실패 0. 리더가 r1 로 옮겨졌다
클라이언트가 붙은 노드(r1) 한 건 실패(AlreadyClosedException … Connection reset) 뒤 1 초 만에 r2 로 다시 붙어 이어졌다(확인 358 · 실패 1)
  • 주소 목록은 섞어서 쓰므로, 앱마다 다른 노드에 붙는다
  • 복구는 연결 · 채널을 되살리지만, 끊기던 순간 보낸 메시지는 실패로 돌아온다. 앱이 다시 보낸다

연결 시간 제한을 기본값(60 초) 으로 두었을 때는 30 초가 넘도록 다시 붙지 못했다. 복구가 죽은 노드의 주소로 붙으려다 기다린 것이다.

7.2s 실패 AlreadyClosedException: connection is already closed due to connection error; cause: java.net.SocketException: Connection reset
8.2s 복구 시작
8.4s 실패 AlreadyClosedException: …
…
39.3s 실패 AlreadyClosedException: …
  • JVM 은 찾은 이름의 IP 를 한동안 기억한다. 컨테이너가 없어진 뒤에도 r3 를 옛 IP 172.19.0.8 로 찾았고, 그 IP 로 붙기가 60.0 초 뒤 SocketTimeoutException: Connect timed out 이었다. 서버가 꺼진 기계도 같다 — 답이 없는 주소에 붙으려 기다린다
  • setConnectionTimeout(3000) 처럼 줄여 두면 죽은 노드를 빨리 건너뛴다

classic 큐 · 노드 둘

살아 있는 노드 q.orders(quorum) q.classic(r2 에 있음)
셋 중 둘 (r3 꺼짐) 보내기 · 받기 됨 보내기 · 받기 됨
셋 중 둘 (r2 꺼짐) 보내기 ack · 받기 됨 (리더가 r1 로) 보내기 바로 nack, 받기는 71.8 초 뒤 NOT_FOUND - failed to perform operation on queue 'q.classic' in vhost '/' due to timeout
셋 중 하나 (r1 만) 보내기는 8 초 안에 확인이 오지 않음, 받기는 56.9 초 뒤 INTERNAL_ERROR - Cannot get a message from queue … nodedown 위와 같음
  • classic 큐는 그 노드 하나가 죽으면 클러스터가 살아 있어도 쓰지 못한다. 잃어도 되는 일시 자료가 아니면 quorum 큐를 쓴다
  • quorum 큐도 과반을 잃으면 멈춘다. 셋이면 하나까지, 다섯이면 둘까지 잃어도 된다
  • INTERNAL_ERROR 는 채널이 아니라 연결을 닫는다. 같은 연결의 다른 채널도 함께 닫혔다
