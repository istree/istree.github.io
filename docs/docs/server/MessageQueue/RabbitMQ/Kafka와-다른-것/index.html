Kafka와 다른 것

RabbitMQ 와 Kafka 는 둘 다 메시지를 맡아 두었다가 건네주지만, 맡는 꼴이 다르다. RabbitMQ 는 큐다 — 교환기가 메시지를 큐로 나눠 넣고, 컨슈머가 ack 하면 지운다. Kafka 는 로그다 — 메시지를 파티션 끝에 덧붙여 보존 기간 동안 두고, 컨슈머 그룹마다 어디까지 읽었는지만 따로 적는다. 그래서 "일을 나눠 한 번씩 처리" 는 RabbitMQ 가 쉽고, "같은 이벤트를 여러 서비스가 저마다 · 나중에 다시 읽기" 는 Kafka 가 쉽다. 아래는 같은 Docker 네트워크에 띄운 rabbitmq:4.4-management(4.4.0) 노드 셋과 apache/kafka:4.4.0 브로커 셋을 Java 클라이언트로 다뤄 본 결과다.

메시지를 맡는 꼴

RabbitMQ Kafka
받은 뒤 ack 하면 지운다. 10 만 개를 받자 큐가 0 이었다 남는다. 10 만 개를 두 번 받은 뒤에도 토픽에 20 만 개(파티션마다 6 만 ~ 6 만 8 천) 가 있었다
다시 읽기 없다 (지웠다) offset 을 되돌리거나(--reset-offsets) 새 그룹으로 처음부터
여러 서비스가 같은 메시지를 서비스마다 큐를 두고 fanout · topic 교환기로 묶는다 서비스마다 그룹을 둔다. 토픽은 하나
나눠 받는 단위 메시지 하나씩, 컨슈머 수에 한도 없음 파티션째, 그룹의 컨슈머는 파티션 수까지만 일한다
일을 고르게 나누기 prefetch 1 이면 빠른 컨슈머가 20 개 중 18 개 파티션마다 정해진 컨슈머가 읽는다. 느린 컨슈머의 파티션은 LAG 이 쌓인다
어디로 보낼지 교환기 · 바인딩 · 라우팅 키 꼴(order.* · #) 토픽 이름. 키는 파티션을 정할 뿐이다
순서 큐 하나 · 컨슈머 하나일 때 넣은 순서 파티션 안에서 넣은 순서. 같은 키는 같은 파티션
처리 실패 basicNack → 다시 넣거나 dead letter 큐로 커밋하지 않으면 그 자리부터 다시. 한 메시지만 빼려면 앱이 다른 토픽에 따로 보낸다
오래 쌓이기 큐 길이 · 메모리 한도. 메모리 경보에 보내기가 멈춘다 보존 기간 · 크기 동안 디스크에. 오래된 세그먼트부터 지운다

장애 때

RabbitMQ (quorum 큐) Kafka (복제 계수 3 · min.insync.replicas=2)
복제 큐마다 노드 셋, 리더 하나 파티션마다 브로커 셋, 리더 하나
성공의 뜻 confirm 의 ack — 과반이 받았다 acks=all — ISR 이 모두 받았다
리더를 죽이면 리더가 옮겨지고 280 건 모두 확인. 붙어 있던 노드가 죽으면 한 건 실패 뒤 1 초 만에 다시 붙었다 13 초쯤 멈추고 한 건 실패(시간 제한 10 초). 기본값이면 실패 없이 한 건이 35.7 초
셋 중 하나만 남으면 확인이 오지 않는다 acks=all 은 시간 초과, acks=1 은 됐다
복제 없는 쪽 classic 큐는 그 노드가 죽으면 바로 nack 복제 계수 1 인 토픽은 그 브로커가 죽자 Leader: none 이 되고 보내기가 시간 초과
  • 둘 다 "과반이 받은 것만 성공" 으로 두면 노드 하나를 잃어도 메시지를 잃지 않고, 둘을 잃으면 쓰기가 멈춘다
  • 둘 다 메시지는 적어도 한 번 온다. RabbitMQ 는 ack 전에 죽은 컨슈머의 메시지가 redelivered 로, Kafka 는 커밋 전에 죽은 컨슈머의 메시지가 다음 컨슈머에게 다시 온다

빠르기

100 바이트짜리 메시지 10 만 개를 Java 클라이언트 하나로 보내고 받았다. 보내기는 둘 다 복제를 마쳤다는 확인을 받는 방식(Kafka acks=all · 파티션 셋, RabbitMQ quorum 큐 · confirm 을 1000 개까지 겹쳐 기다림) 이다.

보내기 받기
Kafka (브로커 셋, 복제 3) 6.5 · 5.8 초 4.7 · 5.3 초
RabbitMQ quorum 큐 (노드 셋, 복제 3) 10.5 · 15.7 초 3.3 · 4.3 초
RabbitMQ classic 큐 (복제 없음) 3.5 초 2.7 초
  • 두 번 잰 값이다. 노드 셋 · 브로커 셋 · 클라이언트가 모두 CPU 2 개짜리 가상 머신 하나에서 돌아, 실제 서버의 빠르기와는 다르다. 설정도 기본값 그대로다
  • Kafka 의 받기에는 그룹에 들어가는 시간(리밸런스) 이 들어 있다
  • 이 정도 양에서는 빠르기가 선택의 까닭이 되지 않았다. 선택의 까닭은 위의 「맡는 꼴」 이다

언제 무엇을

할 일 맞는 쪽
이메일 · 썸네일 같은 작업을 일꾼 여럿이 나눠 처리 RabbitMQ — prefetch · ack · dead letter
메시지마다 받을 곳을 규칙으로 나누기 RabbitMQ — topic 교환기
주문 · 결제 이벤트를 여러 서비스가 저마다 받기 Kafka — 그룹마다 따로 읽는다
지난 이벤트를 다시 처리 · 새 서비스가 처음부터 읽기 Kafka — 보존 · offset 되돌리기
로그 · 클릭처럼 많이 쌓이는 기록 모으기 Kafka
  • RabbitMQ 의 stream 큐(x-queue-type: stream) 는 Kafka 처럼 받아도 지우지 않는 로그다. RabbitMQ 를 이미 쓰는데 다시 읽기만 필요하면 이것을 본다
