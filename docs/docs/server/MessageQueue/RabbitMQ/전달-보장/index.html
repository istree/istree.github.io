RabbitMQ 는 컨슈머가 처리했다고 알릴 때(ack) 메시지를 큐에서 지운다. ack 를 보내기 전에 컨슈머가 죽으면 메시지는 큐로 돌아가 다른 컨슈머가 다시 받는다. 그래서 수동 ack 를 쓰면 메시지를 잃지 않는 대신 두 번 받을 수 있다. 처리할 수 없는 메시지는 dead letter 교환기로 빼고, 컨슈머마다 한 번에 쥘 수(prefetch) 를 정해 일을 고르게 나눈다. 보내는 쪽은 publisher confirm 으로 브로커가 받았는지 확인한다. 서버를 다시 띄웠을 때 남는지는 큐와 메시지의 성질에 따라 다르다. 아래 예제는 rabbitmq:4.4-management(4.4.0) 노드 하나와 Java 클라이언트(amqp-client 5.37.1) 로 돌렸다.

ack

메시지 다섯을 넣고, 둘을 처리한 뒤 셋째를 처리하다 연결이 끊기게 했다.

ch.basicConsume("q.work", false, (tag, d) -> {     // autoAck = false
    handle(d);
    ch.basicAck(d.getEnvelope().getDeliveryTag(), false);
}, tag -> {});
방식 받은 것 끊긴 뒤 큐에 남은 것
수동 ack (autoAck=false) m0 ~ m4 (m0 · m1 만 ack) 3 개 — m2 · m3 · m4 가 redelivered=true 로 다시 왔다
자동 ack (autoAck=true) m0 ~ m4 0 개 — 처리하지 못한 셋을 잃었다
  • 자동 ack 는 서버가 메시지를 보내는 순간 지운다. 처리 중에 죽으면 잃는다
  • 수동 ack 에서 다시 온 메시지는 getEnvelope().isRedeliver() 가 true 다. 앞서 처리하다 죽었을 수 있으니, 받는 쪽은 같은 메시지를 두 번 처리해도 괜찮게 만든다
  • 수동 ack 는 끝까지 보내야 한다. ack 를 빠뜨린 메시지는 unacked 로 남아 다른 컨슈머에게 가지 않는다. 서버는 ack 없이 consumer_timeout(기본 1800000, 30 분) 이 지나면 그 컨슈머에 손을 쓴다(4.4 의 설정값 consumer_timeout_response: notify_consumer)

prefetch

처리가 느린 컨슈머(500 ms) 와 빠른 컨슈머(50 ms) 를 함께 띄우고 메시지 20 개를 넣었다.

ch.basicQos(1);     // ack 하지 않은 메시지를 하나까지만 쥔다
prefetch 느린 쪽 빠른 쪽 다 끝난 시간
없음 10 10 5.0 초
1 2 18 0.8 초
  • prefetch 가 없으면 서버는 메시지를 차례로 나눠 미리 다 보낸다. 느린 쪽이 받아 둔 10 개를 끝낼 때까지 빠른 쪽은 놀았다
  • prefetch 를 정하면 ack 한 만큼만 더 받으므로, 빨리 끝내는 쪽이 더 많이 가져간다. 작업 큐에는 꼭 정한다. 한 건이 짧은 일은 10 ~ 100 쯤으로 두어 오가는 시간을 줄인다

처리할 수 없는 메시지

ch.basicNack(tag, false, true);     // 다시 큐에 넣는다
ch.basicNack(tag, false, false);    // 버린다 (dead letter 교환기가 있으면 그쪽으로)
  • 다시 넣으면(requeue=true) 곧바로 다시 온다. 늘 실패하는 메시지는 컨슈머와 큐 사이를 끝없이 돈다. 몇 번 실패했는지 보고 버린다

큐에 dead letter 교환기를 정해 두면, 버린 · 만료된 · 넘친 메시지가 그쪽으로 간다.

ch.exchangeDeclare("dlx", BuiltinExchangeType.FANOUT, true);
ch.queueDeclare("q.dead", true, false, false, null);
ch.queueBind("q.dead", "dlx", "");

ch.queueDeclare("q.main", true, false, false, Map.of("x-dead-letter-exchange", "dlx"));
ch.queueDeclare("q.ttl", true, false, false, Map.of("x-dead-letter-exchange", "dlx", "x-message-ttl", 1000));
ch.queueDeclare("q.short", true, false, false, Map.of("x-dead-letter-exchange", "dlx", "x-max-length", 3));

q.main 에서 하나를 basicNack(…, false) 하고, q.ttl 에 하나를 넣고 1.5 초 기다리고, q.short 에 다섯을 넣었다.

q.main=0 q.ttl=0 q.short=3 q.dead=4
dead bad · 이유 rejected · 큐 q.main
dead s0 · 이유 maxlen · 큐 q.short
dead s1 · 이유 maxlen · 큐 q.short
dead late · 이유 expired · 큐 q.ttl
  • 까닭과 원래 큐가 x-death 머리말에 담긴다. dead letter 큐를 지켜보면 무엇이 왜 실패했는지 안다
  • 길이 한도를 넘으면 기본으로 가장 오래된 메시지(앞) 를 뺀다. 새 메시지를 거절하려면 x-overflow: reject-publish 를 준다(아래)
  • 같은 인자는 큐마다 주지 않고 정책으로 한 번에 건다(rabbitmqctl set_policy DLX "^q\." '{"dead-letter-exchange":"dlx"}' --apply-to queues). 정책은 이미 있는 큐에도 걸린다

publisher confirm

ch.confirmSelect();
ch.basicPublish("", "q.full", MessageProperties.PERSISTENT_TEXT_PLAIN, body);
boolean ok = ch.waitForConfirms(5000);      // true = ack, false = nack

길이 한도 2 · x-overflow: reject-publish 인 큐에 넷을 보냈다.

f0 확인 ack
f1 확인 ack
f2 확인 nack
f3 확인 nack
  • confirm 이 없으면 셋째 · 넷째가 거절된 것을 보내는 쪽은 모른다
  • 하나 보낼 때마다 기다리면 느리다. persistent 메시지 10000 개를 보내는 데 하나씩 기다리면 9.1 초, 100 개마다 기다리면 0.7 초였다. 많이 보낼 때는 묶어서 기다리거나 addConfirmListener 로 따로 받는다
  • 클러스터에서 quorum 큐의 ack 는 노드 과반이 받은 뒤에 온다

다시 띄우면

durable classic 큐와 quorum 큐에 persistent 메시지와 transient 메시지를 하나씩 넣고 서버를 다시 띄웠다.

큐 넣은 뒤 다시 띄운 뒤
classic, durable 2 1 — transient 메시지가 사라졌다
quorum 2 2 
ch.basicPublish("", q, MessageProperties.PERSISTENT_TEXT_PLAIN, body);   // deliveryMode 2
ch.basicPublish("", q, MessageProperties.TEXT_PLAIN, body);              // deliveryMode 1 (transient)
  • classic 큐에 남기려면 큐는 durable, 메시지는 persistent 로 보낸다. 둘 중 하나라도 빠지면 다시 띄울 때 잃는다
  • quorum 큐는 메시지를 늘 디스크에 남긴다
  • persistent 라도 서버가 디스크에 쓰기 전에 죽으면 잃을 수 있다. 잃으면 안 되는 메시지는 confirm 의 ack 를 받은 뒤에 보낸 것으로 친다
