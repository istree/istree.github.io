RabbitMQ 에서 프로듀서는 메시지를 큐가 아니라 교환기(exchange) 에 보낸다. 메시지에는 라우팅 키가 붙고, 교환기는 큐와 맺은 바인딩을 보고 어느 큐에 넣을지 정한다. 교환기 종류에 따라 정하는 법이 다르다 — direct 는 키가 같은 큐로, topic 은 키의 꼴이 맞는 큐로, fanout 은 묶인 큐 모두로 보낸다. 컨슈머는 큐에서 받는다. 보낼 큐가 하나도 없는 메시지는 따로 말하지 않으면 조용히 사라진다. 아래 예제는 rabbitmq:4.4-management(4.4.0) 와 Java 클라이언트(amqp-client 5.37.1) 로 돌렸다.

큐 만들기

ch.queueDeclare("q.paid", true, false, false, null);   // 이름, durable, exclusive, autoDelete, 인자
인자 뜻
durable 서버를 다시 띄워도 큐가 남는다
exclusive 이 연결만 쓰고, 연결이 끊기면 지워진다
autoDelete 마지막 컨슈머가 떠나면 지워진다
x-queue-type classic(기본) · quorum(복제) · stream(로그)
  • 같은 이름 · 같은 인자로 다시 queueDeclare 하면 아무 일도 없다. 인자가 다르면 PRECONDITION_FAILED - inequivalent arg 'x-queue-type' for queue 'q.pre' in vhost '/': received 'quorum' but current is 'classic' 로 채널이 닫힌다. 앱이 띄울 때마다 선언해 두는 것이 보통이다
  • 4.4 에서 durable 이 아니고 exclusive 도 아닌 큐는 만들 수 없었다. INTERNAL_ERROR - Feature transient_nonexcl_queues is deprecated. 로 연결이 끊겼다. rabbitmq-diagnostics list_deprecated_features 에 transient_nonexcl_queues · denied_by_default 로 나온다. 잠깐 쓸 큐는 exclusive 로 만든다

기본 교환기

이름이 빈 교환기("") 는 큐 이름을 라우팅 키로 받아 그 큐에 넣는다. 모든 큐가 저절로 여기에 묶여 있다.

ch.basicPublish("", "hello", null, "hello".getBytes());
GetResponse g = ch.basicGet("hello", true);
// 받음 hello · 교환기 '' · 키 hello
  • 큐 하나에 바로 넣는 것처럼 쓰는 길이다. 받는 큐가 늘어날 일이 있으면 처음부터 교환기를 둔다

direct

ch.exchangeDeclare("orders.direct", BuiltinExchangeType.DIRECT, true);
ch.queueBind("q.paid", "orders.direct", "paid");
ch.queueBind("q.shipped", "orders.direct", "shipped");
// 키 paid · shipped · paid · cancelled 를 보냈다
q.paid=2 q.shipped=1
  • 키가 바인딩 키와 같은 큐로만 간다. cancelled 는 묶인 큐가 없어 사라졌다
  • 큐 하나에 바인딩을 여럿 걸 수도 있고, 같은 키에 큐 여럿을 걸면 모두 받는다

topic

라우팅 키를 점으로 나눈 낱말로 보고, 바인딩 키의 *(낱말 하나) · #(낱말 0 개 이상) 으로 맞춘다.

ch.exchangeDeclare("events", BuiltinExchangeType.TOPIC, true);
ch.queueBind("q.all", "events", "#");
ch.queueBind("q.order", "events", "order.*");
ch.queueBind("q.kr", "events", "*.kr.#");
// 키 order.created · order.kr.paid · user.kr · user.created 를 보냈다
q.all=4 q.order=1 q.kr=2
q.order ← [order.created]
q.kr ← [order.kr.paid, user.kr]
  • order.* 는 낱말이 꼭 둘이라 order.kr.paid 를 받지 않았다. 셋 이상도 받으려면 order.# 이다
  • *.kr.# 의 # 은 0 개도 되므로 user.kr 을 받았다
  • 키는 무엇.어디.무슨일 처럼 넓은 것부터 좁은 것으로 짓는다. 나중에 받는 쪽이 늘어도 바인딩만 더한다

fanout

ch.exchangeDeclare("broadcast", BuiltinExchangeType.FANOUT, true);
ch.queueBind("q.a", "broadcast", "");
ch.queueBind("q.b", "broadcast", "");
ch.basicPublish("broadcast", "anything", null, "x".getBytes());
// q.a=1 q.b=1
  • 키를 보지 않고 묶인 큐 모두에 한 벌씩 넣는다. 한 이벤트를 여러 서비스가 저마다 받을 때 쓴다. 서비스마다 제 큐를 하나씩 묶는다

갈 곳 없는 메시지

ch.addReturnListener(r -> log("돌아옴 " + r.getReplyCode() + " " + r.getReplyText() + " 키 " + r.getRoutingKey()));
ch.basicPublish("orders.direct", "cancelled", false, null, body);   // 조용히 사라진다
ch.basicPublish("orders.direct", "cancelled", true, null, body);    // mandatory
// 돌아옴 312 NO_ROUTE 키 cancelled
  • mandatory 를 켜면 갈 큐가 없는 메시지를 프로듀서에게 돌려준다. 켜지 않으면 오류도 기록도 없다. 바인딩을 빠뜨린 것을 알아채려면 켠다
  • 교환기에 alternate-exchange 인자를 주면 갈 곳 없는 메시지를 다른 교환기로 보낸다. 묶인 큐가 없는 키로 보내자 그 교환기에 묶은 q.unrouted 에 들어갔다

없는 교환기에 보내면 채널이 닫힌다.

channel error; protocol method: #method<channel.close>(reply-code=404, reply-text=NOT_FOUND - no exchange 'nope' in vhost '/', class-id=60, method-id=40)
  • basicPublish 는 바로 돌아오고, 오류는 그 채널의 다음 명령에서 드러났다

받기

ch.basicConsume("q.paid", false, (tag, d) -> {
    handle(new String(d.getBody(), StandardCharsets.UTF_8));
    ch.basicAck(d.getEnvelope().getDeliveryTag(), false);
}, tag -> {});
  • basicConsume 은 서버가 메시지를 밀어 준다. basicGet 은 하나씩 당겨 오는 것이라 시험 · 도구에만 쓴다
  • 한 큐에 컨슈머가 여럿이면 메시지를 차례로 나눠 준다. 같은 메시지를 여러 곳이 받아야 하면 큐를 여럿 두고 fanout · topic 으로 묶는다
