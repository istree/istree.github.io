컨슈머 그룹

Kafka 의 컨슈머는 그룹(group.id) 으로 묶인다. 한 그룹 안에서는 토픽의 파티션을 컨슈머들이 나눠 가지므로, 메시지 하나는 그룹마다 한 컨슈머에게만 간다. 컨슈머를 더하면 일이 나뉘고, 하나가 죽으면 남은 컨슈머가 그 파티션을 넘겨받는다(리밸런스). 그룹은 파티션마다 어디까지 읽었는지(offset) 를 브로커에 커밋해 둔다. 다른 그룹은 같은 토픽을 처음부터 따로 읽는다. 커밋하기 전에 죽은 컨슈머가 처리한 메시지는 다음 컨슈머가 다시 받으므로, 메시지는 적어도 한 번 온다. 아래 예제는 apache/kafka:4.4.0 브로커 한 대, 파티션 셋짜리 토픽 events 와 Java 클라이언트(kafka-clients 4.4.0) 로 돌렸다.

컨슈머

var props = new Properties();
props.put("bootstrap.servers", "k1:19092");
props.put("group.id", "g1");
props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("auto.offset.reset", "earliest");     // 커밋된 offset 이 없으면 처음부터

try (var c = new KafkaConsumer<String, String>(props)) {
    c.subscribe(List.of("events"), new ConsumerRebalanceListener() {
        public void onPartitionsRevoked(Collection<TopicPartition> p) { System.out.println("내놓음 " + p); }
        public void onPartitionsAssigned(Collection<TopicPartition> p) { System.out.println("받음 " + p); }
    });
    while (true) {
        for (ConsumerRecord<String, String> r : c.poll(Duration.ofMillis(500)))
            System.out.printf("p%d o%d %s=%s%n", r.partition(), r.offset(), r.key(), r.value());
    }
}
  • poll 이 메시지를 묶음으로 가져온다. 기본은 enable.auto.commit=true 라, 5 초(auto.commit.interval.ms) 마다 다음 poll 에서 앞서 받은 것까지 커밋한다
  • auto.offset.reset 의 기본은 latest 다. 새 그룹 g3 을 그대로 띄우자 이미 있던 메시지는 하나도 받지 않았다(Processed a total of 0 messages). 처음부터 읽을 그룹은 earliest 로 둔다

리밸런스

컨슈머 A 를 띄우고 12 초 뒤 B, 다시 12 초 뒤 C · D 를 띄웠다. C · D 는 14 초, B 는 28 초 뒤 끝나게 했다.

그때 A B C D
A 만 0 · 1 · 2
B 가 들어옴 2 0 · 1
C · D 가 들어옴 2 0 1 (없음)
C · D 가 나감 2 0 · 1
B 가 나감 0 · 1 · 2
  • 파티션(셋) 보다 많은 컨슈머(넷) 는 빈 목록 [] 을 받고 논다. 그룹의 컨슈머 수는 파티션 수까지만 의미가 있다
  • 기본 방식(group.protocol=classic) 에서는 리밸런스 때마다 모든 컨슈머가 가진 파티션을 다 내놓고 다시 받았다(A 가 내놓음 [0, 1, 2] 뒤 받음 [2]). 그동안 그룹 전체가 잠깐 멈춘다

4.0 부터 쓸 수 있는 새 방식은 옮길 파티션만 옮긴다.

props.put("group.protocol", "consumer");
A 받음 [0, 1, 2]
A 내놓음 [2]          ← B 가 들어옴. 0 · 1 은 그대로 쥐고 있다
B 받음 [2]
  • 그룹의 방식은 kafka-consumer-groups.sh --describe --group g4 --state 의 ASSIGNMENT-STRATEGY 에 uniform 으로 보였다
  • 콘솔 컨슈머도 띄울 때마다 The consumer rebalance protocol (KIP-848) is production-ready! Set group.protocol=consumer to try it out. 를 알린다

LAG

kafka-consumer-groups.sh --bootstrap-server k1:19092 --describe --group g1
Consumer group 'g1' has no active members.
GROUP  TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID  HOST  CLIENT-ID
g1     events  0          2               5               3    -            -     -
g1     events  1          2               5               3    -            -     -
g1     events  2          2               5               3    -            -     -
  • CURRENT-OFFSET 은 그룹이 커밋한 다음 읽을 자리, LOG-END-OFFSET 은 파티션의 끝이다. 그 차이(LAG) 가 아직 처리하지 않은 메시지 수다. 그룹이 멈춘 사이 9 개를 보내자 파티션마다 3 씩 쌓였다
  • LAG 이 계속 늘면 컨슈머가 따라가지 못하는 것이다. 컨슈머를 파티션 수까지 늘리거나, 처리를 빠르게 하거나, 파티션을 늘린다. 모니터링에 이 값을 넣는다

처리 중에 죽으면

자동 커밋을 끄고(enable.auto.commit=false) poll 한 묶음을 다 처리한 뒤 commitSync() 하는 컨슈머로, 넷째 메시지를 처리하고 커밋 전에 죽게 했다.

for (ConsumerRecord<String, String> r : c.poll(Duration.ofMillis(500))) {
    handle(r);
}
c.commitSync();          // 묶음을 다 처리한 뒤 커밋
A p0 o2 u2=msg-2
A p0 o3 u4=msg-4
A p0 o4 u2=msg-8
A p1 o2 u1=msg-1
A 죽음 (커밋 안 함)

같은 그룹으로 새 컨슈머를 띄웠다.

45s A2 받음 [0, 1, 2]
45s A2 p0 o2 u2=msg-2     ← A 가 처리한 넷을 다시 받았다
45s A2 p0 o3 u4=msg-4
45s A2 p0 o4 u2=msg-8
45s A2 p1 o2 u1=msg-1
45s A2 p1 o3 u3=msg-3
…
  • 커밋한 자리부터 다시 받으므로 A 가 처리한 네 메시지가 한 번 더 왔다. 받는 쪽은 같은 메시지를 두 번 처리해도 결과가 같게 만든다(주문 번호로 이미 처리했는지 보기 · upsert)
  • 새 컨슈머는 45 초 동안 아무것도 받지 못했다. 브로커는 죽은 A 가 session.timeout.ms(기본 45000) 동안 소식이 없어야 그룹에서 빼고 파티션을 다시 나눈다. 제대로 끝낸(close()) 컨슈머는 바로 빠진다
  • 커밋을 처리보다 먼저 하면 반대로 죽은 뒤 그 메시지를 잃는다(at-most-once). 보통은 처리한 뒤에 커밋한다

다시 읽기

그룹이 멈춘 동안 offset 을 옮겨 지난 메시지를 다시 읽힌다.

kafka-consumer-groups.sh --bootstrap-server k1:19092 --group g1 --topic events \
  --reset-offsets --to-earliest --dry-run      # 바꿀 자리만 보인다
kafka-consumer-groups.sh --bootstrap-server k1:19092 --group g1 --topic events \
  --reset-offsets --to-earliest --execute
옵션 옮길 자리
--to-earliest · --to-latest 처음 · 끝
--to-datetime 2026-01-01T00:00:00.000 그 시각 뒤의 첫 메시지
--shift-by -100 지금에서 100 개 앞
--to-offset 42 그 번호
--topic events:0 파티션 0 만
  • 그룹에 살아 있는 컨슈머가 있으면 Error: Assignments can only be reset if the group 'g1' is inactive, but the current state is Stable. 다. 컨슈머를 모두 멈춘 뒤에 한다
  • 처음보다 앞으로 옮기면 WARN New offset (-1) is lower than earliest offset for topic partition events-0. Value will be set to 0. 를 남기고 처음으로 맞춘다
  • 다른 처리를 새로 붙일 때는 offset 을 되돌리지 않고 새 그룹으로 처음부터 읽는다. 기존 그룹의 자리는 그대로다
