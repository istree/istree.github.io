Kafka 클러스터는 브로커 여럿이 파티션을 나눠 가진 묶음이다. 복제 계수가 3 이면 파티션마다 브로커 셋이 사본을 갖고, 그중 하나(리더) 가 읽기 · 쓰기를 받고 나머지(팔로어) 가 따라 쓴다. 리더를 잘 따라오는 사본의 목록이 ISR 이다. 프로듀서가 acks=all 로 보내면 ISR 이 모두 받아야 성공이고, min.insync.replicas=2 를 함께 두면 ISR 이 둘보다 적을 때 쓰기를 거절해 메시지를 잃지 않는다. 리더 브로커가 죽으면 컨트롤러가 ISR 에서 새 리더를 고른다. 4.0 부터 컨트롤러도 Kafka 노드가 맡고(KRaft), 컨트롤러끼리도 과반이 있어야 일한다. 아래 예제는 apache/kafka:4.4.0 브로커 셋(kb1 · kb2 · kb3, 저마다 브로커 겸 컨트롤러, 힙 512 MB) 과 Java 프로듀서(kafka-clients 4.4.0) 로 돌렸다.

띄우기

세 노드에 같은 CLUSTER_ID 와 같은 컨트롤러 목록을 준다.

CID=$(docker run --rm apache/kafka:4.4.0 /opt/kafka/bin/kafka-storage.sh random-uuid)   # HAmQccNQQO6ynHP1MFxn_w

for i in 1 2 3; do
  docker run -d --name kb$i --hostname kb$i --network kafka-net \
    -e CLUSTER_ID=$CID -e KAFKA_NODE_ID=$i -e KAFKA_PROCESS_ROLES=broker,controller \
    -e KAFKA_LISTENERS=INTERNAL://:19092,CONTROLLER://:9093 \
    -e KAFKA_ADVERTISED_LISTENERS=INTERNAL://kb$i:19092 \
    -e KAFKA_LISTENER_SECURITY_PROTOCOL_MAP=INTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT \
    -e KAFKA_INTER_BROKER_LISTENER_NAME=INTERNAL -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER \
    -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@kb1:9093,2@kb2:9093,3@kb3:9093 \
    -e KAFKA_DEFAULT_REPLICATION_FACTOR=3 -e KAFKA_MIN_INSYNC_REPLICAS=2 \
    -e KAFKA_LOG_DIRS=/var/lib/kafka/data -e KAFKA_HEAP_OPTS="-Xmx512m -Xms512m" \
    -v kb$i-data:/var/lib/kafka/data apache/kafka:4.4.0
done
kafka-metadata-quorum.sh --bootstrap-server kb1:19092 describe --status
LeaderId:               1
CurrentVoters:          [{"id": 1, …"CONTROLLER://kb1:9093"]}, {"id": 2, …}, {"id": 3, …}]
  • 세 노드 모두 15 초 안에 Kafka Server started 였다. 노드마다 메모리는 300 MB 쯤이었다
  • 컨트롤러 셋 가운데 하나(LeaderId: 1) 가 메타데이터를 쓰고 나머지가 따라 쓴다. 노드가 많은 클러스터는 컨트롤러 셋 · 브로커 여럿으로 역할을 나눈다(KAFKA_PROCESS_ROLES=controller · broker)
  • 클라이언트에는 bootstrap.servers=kb1:19092,kb2:19092,kb3:19092 처럼 둘셋을 적는다. 하나가 죽어도 처음 연결이 된다

리더와 ISR

kafka-topics.sh --bootstrap-server kb1:19092 --create --topic pay --partitions 3    # 복제 계수는 기본 3
kafka-topics.sh --bootstrap-server kb1:19092 --describe --topic pay
	Topic: pay	Partition: 0	Leader: 3	Replicas: 3,1,2	Isr: 3,1,2
	Topic: pay	Partition: 1	Leader: 1	Replicas: 1,2,3	Isr: 1,2,3
	Topic: pay	Partition: 2	Leader: 2	Replicas: 2,3,1	Isr: 2,3,1
  • 파티션마다 리더가 다른 브로커에 있어 쓰기가 셋에 나뉜다
  • Replicas 의 첫 브로커가 원래 리더다. 리더가 바뀌었다가 그 브로커가 돌아오면 원래 리더로 되돌린다(auto.leader.rebalance.enable=true, 검사 간격 leader.imbalance.check.interval.seconds=300). 파티션 0 의 리더가 몇 분 뒤 kb3 로 돌아와 있었다

리더 브로커를 죽이기

acks=all 로 0.1 초마다 파티션 0 에 보내면서, 파티션 0 의 리더 kb3 를 docker kill 했다.

6.9s 실패 TimeoutException: Expiring 1 record(s) for pay-0:10002 ms has passed since batch creation.
17.0s 성공 (3089 ms 걸림) offset 44
성공 128 · 실패 1
	Topic: pay	Partition: 0	Leader: 1	Replicas: 3,1,2	Isr: 1,2
  • 새 리더(kb1) 가 정해지기까지 쓰기가 13 초쯤 멈췄다. 그 사이 한 건은 프로듀서의 delivery.timeout.ms 를 넘겨 실패했다. 이 시험은 delivery.timeout.ms=10000 · request.timeout.ms=3000 으로 줄여 돌렸다
  • 컨트롤러는 브로커가 broker.session.timeout.ms(기본 9000) 동안 소식이 없어야 죽은 것으로 보고 리더를 옮긴다
  • 제대로 끄면(docker stop) 브로커가 끄기 전에 리더를 넘긴다. 같은 시험에서 kb3 를 docker stop 하자 208 건이 모두 성공했고, 가장 오래 걸린 것이 0.6 초였다
  • 클라이언트 시간 제한을 기본값(delivery.timeout.ms 120 초 · request.timeout.ms 30 초) 으로 두고 리더를 kill 하자 실패는 없었지만 한 건이 35.7 초 걸렸다. 죽은 리더에게 보낸 요청의 답을 30 초 기다린 뒤 새 리더로 다시 보냈다. 앱의 요청 시간 제한이 이보다 짧으면 그쪽에서 실패한다
  • kb3 를 다시 띄우자 15 초 뒤 ISR 이 1,2,3 으로 돌아왔다. 빠진 동안의 메시지를 리더에서 받아 따라잡는다

min.insync.replicas

min.insync.replicas=3 인 토픽 strict 를 만들고 브로커 하나를 껐다. ISR 이 1,2 둘이 되었다.

보낸 것 결과
acks=all 브로커가 NOT_ENOUGH_REPLICAS 로 거절하고, 프로듀서가 되풀이해 다시 보내다 delivery.timeout.ms 뒤 TimeoutException
acks=1 성공 — 리더 혼자 받으면 된다 
WARN … Got error produce response with correlation id 6 on topic-partition strict-0, retrying (2147483646 attempts left). Error: NOT_ENOUGH_REPLICAS
  • acks=all 과 min.insync.replicas 가 함께 있어야 "성공한 메시지는 브로커 둘 이상에 있다" 가 된다. acks=all 만 두면 ISR 이 리더 하나로 줄었을 때 리더 혼자 받고도 성공이다
  • 보통은 복제 계수 3 · min.insync.replicas=2 다. 브로커 하나를 잃어도 쓰기가 이어지고, 성공한 메시지는 두 곳에 있다
  • acks=1 로 성공한 메시지는 팔로어가 받기 전에 리더가 죽으면 사라질 수 있다. 잃어도 되는 로그 · 지표에만 쓴다

둘을 죽이기

kb3 · kb2 를 죽여 kb1 만 남겼다(토픽 pay, min.insync.replicas=2).

보낸 것 결과
둘 살아 있을 때 acks=all 19 건 모두 성공
하나만 남았을 때 acks=all TimeoutException
하나만 남았을 때 acks=1 46 건 모두 성공
  • 컨트롤러도 셋 중 하나만 남아 과반이 아니다. 메타데이터를 바꾸지 못해 ISR 도 1,2 에서 줄지 않았고, 리더는 kb2 의 답을 기다리다 시간이 지났다
  • 브로커를 모두 다시 띄우자 ISR 이 셋으로 돌아왔다. 복제가 덜 된 파티션은 kafka-topics.sh --describe --under-replicated-partitions 로 찾는다(돌아온 뒤에는 빈 결과)

프로듀서 기본값

acks 만 정하고 띄운 프로듀서의 설정 로그다.

	acks = -1
	enable.idempotence = true
	linger.ms = 5
	max.in.flight.requests.per.connection = 5
	retries = 2147483647
  • acks=-1 은 all 이다. 3.0 부터 기본이 all 이고, 멱등(enable.idempotence) 도 켜져 있다. 다시 보내도 브로커가 같은 메시지를 한 번만 적는다
  • retries 는 사실상 끝이 없고, 언제까지 다시 보낼지는 delivery.timeout.ms 가 정한다
  • linger.ms 의 기본은 4.0 부터 5 ms 다. 5 ms 동안 모은 메시지를 한 번에 보낸다
