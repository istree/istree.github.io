토픽과 파티션

Kafka 의 토픽은 파티션 여럿으로 나뉜 로그다. 메시지는 파티션 하나의 끝에 덧붙고, 파티션 안에서 0 부터 늘어나는 번호(offset) 를 받는다. 순서는 파티션 안에서만 지켜진다. 같은 키의 메시지는 늘 같은 파티션으로 가므로, 한 주문 · 한 사용자의 이벤트처럼 순서가 중요한 것은 키를 붙여 보낸다. 메시지는 읽어 가도 지워지지 않고, 보존 기간이 지나거나 크기 한도를 넘으면 오래된 것부터 지워진다. 키마다 마지막 값만 남기는 compaction 토픽도 있다. 아래 예제는 apache/kafka:4.4.0 브로커 한 대와 Java 클라이언트(kafka-clients 4.4.0) 로 돌렸다.

만들기

kafka-topics.sh --bootstrap-server k1:19092 --create --topic orders --partitions 3 --replication-factor 1
kafka-topics.sh --bootstrap-server k1:19092 --describe --topic orders
Topic: orders	TopicId: REwSFMN0TdqBEqXPhPD0RA	PartitionCount: 3	ReplicationFactor: 1	Configs: min.insync.replicas=1
	Topic: orders	Partition: 0	Leader: 1	Replicas: 1	Isr: 1
	Topic: orders	Partition: 1	Leader: 1	Replicas: 1	Isr: 1
	Topic: orders	Partition: 2	Leader: 1	Replicas: 1	Isr: 1
  • 파티션 수는 동시에 읽을 수 있는 컨슈머 수의 한도다. 한 그룹에서 파티션 하나는 컨슈머 하나만 읽는다
  • 복제 계수는 브로커 수를 넘을 수 없다. 브로커 한 대에서는 1 이다

키와 파티션

키 user0 ~ user3 을 두 번씩 보냈다.

RecordMetadata m = p.send(new ProducerRecord<>("orders", "user" + (i % 4), "msg-" + i)).get();
key=user0 → partition 0 offset 1
key=user1 → partition 0 offset 2
key=user2 → partition 2 offset 5
key=user3 → partition 2 offset 6
key=user0 → partition 0 offset 3
key=user1 → partition 0 offset 4
key=user2 → partition 2 offset 7
key=user3 → partition 2 offset 8
  • 키를 해시해 파티션 수로 나눈 나머지가 파티션이다. 같은 키는 몇 번을 보내도 같은 파티션이었다
  • 키 넷 가운데 파티션 1 에 간 키는 없었다. 키 가짓수가 적으면 파티션이 고르게 쓰이지 않는다
  • 키 없이 여섯 번 보내자 여섯 모두 파티션 1 로 갔다. 키가 없으면 한 파티션에 몰아 보내다가 배치가 차면 다른 파티션으로 옮긴다(sticky). 따로 띄운 프로그램은 파티션 0 · 1 로 갔다

파티션 늘리기

kafka-topics.sh --bootstrap-server k1:19092 --alter --topic orders --partitions 6
key=user0 → partition 3     # 전에는 0
key=user1 → partition 0
key=user2 → partition 5     # 전에는 2
key=user3 → partition 5
  • 파티션 수가 바뀌면 나머지가 바뀌어, 같은 키가 다른 파티션으로 간다. 옛 메시지는 옛 파티션에 남으므로, 그 키의 순서가 두 파티션에 걸쳐 갈라진다. 키로 순서를 지키는 토픽은 처음부터 넉넉하게 만든다
  • 줄이기는 안 된다. --partitions 2 는 InvalidPartitionsException: The topic orders currently has 6 partition(s); 2 would not be an increase. 다

보존

kafka-topics.sh --bootstrap-server k1:19092 --create --topic logs --partitions 1 \
  --config retention.ms=15000 --config segment.ms=5000
# 세 줄을 3 초 간격으로 보낸 뒤
kafka-get-offsets.sh --bootstrap-server k1:19092 --topic logs --time -2   # 처음 offset
kafka-get-offsets.sh --bootstrap-server k1:19092 --topic logs --time -1   # 끝 offset
처음 끝
보낸 직후 logs:0:0 logs:0:3
40 초 뒤 logs:0:3 logs:0:3 
INFO [UnifiedLog partition=logs-0, dir=/var/lib/kafka/data] Deleting segment LogSegment(baseOffset=1, size=73, …
  • 15 초가 지난 메시지 셋이 지워졌다. offset 은 다시 0 부터가 아니라 3 에서 이어진다
  • 지우기는 메시지 하나씩이 아니라 세그먼트 파일(segment.ms · segment.bytes 로 나뉨) 째로 한다. 지금 쓰는 세그먼트는 지우지 않는다. 브로커가 지울 것을 찾는 간격은 log.retention.check.interval.ms(기본 5 분) 라, 이 시험에서는 10 초로 줄여 띄웠다
  • 기본 보존은 7 일(retention.ms=604800000) 이고 크기 한도는 없다(retention.bytes=-1). 디스크를 넘지 않게 토픽마다 정한다
설정 뜻
retention.ms 이 시간이 지난 세그먼트를 지운다
retention.bytes 파티션마다 이 크기를 넘으면 오래된 세그먼트부터 지운다
cleanup.policy delete(기본) · compact · compact,delete 
kafka-configs.sh --bootstrap-server k1:19092 --alter --entity-type topics --entity-name logs \
  --add-config retention.ms=86400000      # 만든 뒤 바꾸기

compaction

키마다 마지막 값만 남긴다. 상품 가격 · 사용자 설정처럼 "지금 값" 을 담는 토픽에 쓴다.

kafka-topics.sh --bootstrap-server k1:19092 --create --topic prices --partitions 1 \
  --config cleanup.policy=compact --config segment.ms=3000 \
  --config min.cleanable.dirty.ratio=0.01 --config delete.retention.ms=1000
# apple:1000 · pear:3000 · apple:1200 · milk:2500 · apple:1300 · pear:3100 을 보내고 잠시 뒤
kafka-console-consumer.sh --bootstrap-server k1:19092 --topic prices --from-beginning \
  --formatter-property print.key=true --formatter-property print.offset=true
Offset:3	milk	2500
Offset:4	apple	1300
Offset:5	pear	3100
Offset:6	x	1
  • 같은 키의 옛 값(offset 0 · 1 · 2) 이 지워졌다. 남은 메시지의 offset 은 그대로라 번호가 빈다
  • 값을 null 로 보내면(tombstone) 그 키를 지운다. pear 에 null 을 보내자 pear 가 목록에서 사라졌다
  • 지금 쓰는 세그먼트는 정리하지 않는다. 위 시험은 segment.ms 를 3 초로 줄이고 메시지를 더 보내 세그먼트를 넘긴 뒤에 정리됐다
