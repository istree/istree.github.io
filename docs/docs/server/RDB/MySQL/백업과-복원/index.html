MySQL 의 백업은 대개 mysqldump 로 DB 를 SQL 파일 하나로 떠 두는 것이다. 그 파일을 mysql 에 넣으면 표를 만들고 자료를 다시 넣어 복원된다. 서비스를 멈추지 않고 뜨려면 --single-transaction 을 붙이고, 매일 cron · systemd 타이머로 떠서 다른 곳에 옮겨 둔다. 아래 예제는 mysql:8.4(8.4.13) 컨테이너의 shop DB 로 돌렸다.

뜨기

mysqldump --single-transaction --routines --triggers shop > shop.sql
mysqldump --single-transaction shop | gzip > shop.sql.gz      # 2013 바이트 → 767 바이트

shop.sql 의 중심은 표를 만들고 자료를 넣는 SQL 이다.

DROP TABLE IF EXISTS `orders`;
CREATE TABLE `orders` (
  `id` int NOT NULL AUTO_INCREMENT,
  `item` varchar(20) DEFAULT NULL,
  `qty` int DEFAULT NULL,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB AUTO_INCREMENT=3 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
LOCK TABLES `orders` WRITE;
INSERT INTO `orders` VALUES (1,'사과',3),(2,'배',1);
UNLOCK TABLES;
옵션 뜻
--single-transaction 한 시점의 모습으로 뜬다. InnoDB 표를 잠그지 않아 서비스가 계속 돈다
--routines · --events 저장 프로시저 · 함수, 이벤트도 넣는다 (트리거는 기본으로 들어간다)
--databases a b DB 여럿 — 파일에 CREATE DATABASE · USE 가 들어간다
--all-databases 모든 DB (mysql 시스템 DB 와 사용자 계정 포함)
--no-tablespaces PROCESS 권한이 없는 백업 사용자로 뜰 때
--source-data=2 바이너리 로그 위치를 주석으로 적는다 — 그 뒤의 변경을 이어 붙이는 복구에 쓴다
  • DB 이름만 주면(mysqldump shop) 파일에 CREATE DATABASE 가 없다. 복원할 때 DB 를 먼저 만들어야 한다
  • --databases shop 으로 뜨면 파일에 CREATE DATABASE /*!32312 IF NOT EXISTS*/ `shop` … 과 USE `shop`; 이 들어가 DB 이름째 복원된다
  • 비밀번호는 ~/.my.cnf([client] 의 user · password, 권한 600) 에 두면 명령줄에 남지 않는다

복원

mysql shop < shop.sql
# ERROR 1049 (42000): Unknown database 'shop' — DB 를 지운 뒤라면 먼저 만든다
mysql -e "CREATE DATABASE shop"
gunzip -c shop.sql.gz | mysql shop
mysql --default-character-set=utf8mb4 -e "SELECT item, HEX(item) FROM shop.orders"
# 사과  EC82ACEAB3BC
# 배    EBB0B0
  • 덤프 파일 첫머리에 SET NAMES utf8mb4 가 있어 한글이 그대로 돌아온다. 화면에 ?? 로 보이면 자료가 아니라 보는 클라이언트의 문자셋 문제다
  • 파일의 DROP TABLE IF EXISTS 가 같은 이름의 표를 지우고 다시 만든다. 운영 DB 에 잘못 넣지 않도록 복원은 새 DB 나 다른 서버에서 먼저 해 본다
  • 큰 파일은 pv shop.sql | mysql shop 으로 진행을 본다

Docker 에서

docker exec my mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction shop > shop.sql
docker exec -i my mysql -uroot -p"$MYSQL_ROOT_PASSWORD" shop < shop.sql     # -i 가 있어야 파일이 들어간다
  • 출력을 호스트 파일로 돌리므로 컨테이너 안에 파일이 남지 않는다. 오류도 파일에 섞이지 않게 2>/dev/null 이나 2>dump.err 로 나눈다 — -p 경고(Using a password on the command line interface can be insecure.) 가 stderr 로 나온다

매일 뜨기

#!/bin/sh
# /usr/local/bin/mysql-backup.sh
set -e
d=/var/backups/mysql
mkdir -p $d
mysqldump --single-transaction --routines shop | gzip > $d/shop-$(date +%F).sql.gz
find $d -name "shop-*.sql.gz" -mtime +14 -delete        # 14 일 넘은 것은 지운다
30 3 * * * /usr/local/bin/mysql-backup.sh >> /var/log/mysql-backup.log 2>&1
  • crontab 에 바로 적을 때는 date +\%F 처럼 % 를 \% 로 적는다. 스크립트 안에서는 그대로 쓴다
  • set -e 만으로는 파이프 앞의 mysqldump 실패를 잡지 못한다. bash 로 쓰고 set -o pipefail 을 더하거나, 덤프한 뒤 파일 끝의 -- Dump completed on … 줄이 있는지 본다
  • 백업 파일을 같은 서버에만 두면 디스크가 망가질 때 함께 잃는다. rsync · 오브젝트 저장소로 다른 곳에 옮긴다
  • 복원이 되는지 가끔 실제로 넣어 본다. 떠 두기만 한 백업은 믿을 수 없다
