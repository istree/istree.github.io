Cassandra 의 표는 기본 키가 곧 자료를 두는 자리다. 기본 키의 앞부분인 파티션 키를 해시해 어느 노드에 둘지 정하고, 뒷부분인 클러스터링 키로 파티션 안에서 줄 세워 둔다. 그래서 찾을 때도 파티션 키를 알아야 한다. 파티션 키 없이 다른 열로 찾으면 모든 노드를 훑어야 하므로 막힌다. 관계형 DB 처럼 표를 먼저 짜고 쿼리를 맞추는 것이 아니라, 앱이 할 쿼리를 먼저 적고 쿼리마다 표를 만든다. 같은 자료를 여러 표에 겹쳐 넣는다. 아래 예제는 cassandra:5(5.0.9) 컨테이너의 cqlsh 에서 돌렸다.

키스페이스와 표

CREATE KEYSPACE shop WITH replication = {'class': 'NetworkTopologyStrategy', 'dc1': 1};
USE shop;

-- "사용자 한 명의 주문을 최근 것부터"
CREATE TABLE orders_by_user (
  user_id int, order_time timestamp, item text, qty int,
  PRIMARY KEY ((user_id), order_time)
) WITH CLUSTERING ORDER BY (order_time DESC);
  • 키스페이스는 DB 에 해당하고, 복제 계수(자료를 몇 벌 둘지) 를 여기서 정한다. 노드 하나에서는 1, 운영은 DC 마다 3 이다
  • PRIMARY KEY ((user_id), order_time) 의 안쪽 괄호가 파티션 키, 그 뒤가 클러스터링 키다. 한 사용자의 주문은 모두 한 파티션에 시각 순으로 모인다
  • 파티션 키는 해시 값(토큰) 으로 바뀌어 노드에 나뉜다. SELECT token(user_id), user_id FROM orders_by_user 는 1 → -4069959284402364209, 2 → -3248873570005575792 였다

찾을 수 있는 것과 없는 것

SELECT * FROM orders_by_user WHERE user_id = 1;
 user_id | order_time                      | item  | qty
---------+---------------------------------+-------+-----
       1 | 2026-11-05 09:00:00.000000+0000 |  pear |   1
       1 | 2026-11-01 10:00:00.000000+0000 | apple |   3
조건 결과
WHERE user_id = 1 된다 — 파티션 하나, 최근 것부터
WHERE user_id = 1 AND order_time >= '2026-11-03' 된다 — 파티션 안에서 클러스터링 키의 범위
WHERE item = 'apple' 막힌다
WHERE order_time >= '2026-11-03' 막힌다 — 클러스터링 키만으로는 안 된다
WHERE user_id = 1 AND item = 'apple' 막힌다 — 키가 아닌 열 
InvalidRequest: Error from server: code=2200 [Invalid query] message="Cannot execute this query as it might involve data filtering and thus may have unpredictable performance. If you want to execute this query despite the performance unpredictability, use ALLOW FILTERING"
  • 끝에 ALLOW FILTERING 을 붙이면 돈다. 다만 모든 노드의 모든 파티션을 읽고 걸러 낸다. 자료가 늘수록 느려지므로 앱의 쿼리에는 쓰지 않는다
  • 조인 · GROUP BY 가 없는 열로 묶기 · 하위 쿼리도 없다. 앱에서 표 여럿을 읽어 합친다

쿼리마다 표

"상품 하나가 팔린 주문" 이 필요하면 그 쿼리의 표를 만들고, 주문을 넣을 때 두 표에 함께 넣는다.

CREATE TABLE orders_by_item (
  item text, order_time timestamp, user_id int, qty int,
  PRIMARY KEY ((item), order_time, user_id)
);

BEGIN BATCH
  INSERT INTO orders_by_user (user_id, order_time, item, qty) VALUES (5, '2026-11-09 08:00:00+0000', 'apple', 2);
  INSERT INTO orders_by_item (item, order_time, user_id, qty) VALUES ('apple', '2026-11-09 08:00:00+0000', 5, 2);
APPLY BATCH;

SELECT * FROM orders_by_item WHERE item = 'apple';
  • BATCH 는 묶은 쓰기가 모두 적용되거나 결국 모두 적용되게 한다. 빠르게 하려는 것이 아니라 두 표가 어긋나지 않게 하려고 쓴다. 다른 파티션을 많이 묶으면 오히려 느리다
  • orders_by_item 의 클러스터링 키에 user_id 를 더했다. 같은 시각에 같은 상품을 두 사람이 사면 기본 키가 같아 하나가 덮인다(아래)
  • 한 파티션에 행이 끝없이 쌓이지 않게 한다. 오래 쌓이는 자료는 파티션 키에 날짜를 넣어(((item, day), order_time)) 나눈다

키가 아닌 열로 찾기 (SAI)

5.0 의 SAI(Storage Attached Index) 를 만들면 그 열로 찾을 수 있다.

CREATE INDEX ON orders_by_user (item) USING 'sai';
SELECT * FROM orders_by_user WHERE item = 'apple';
  • 만든 직후에는 ReadFailure: … INDEX_NOT_AVAILABLE 였고, 3 초 뒤에는 결과가 나왔다. 있던 자료로 인덱스를 다 짓기 전에는 쓰지 못한다
  • 인덱스는 노드마다 자기 자료에만 있다. 파티션 키 없이 찾으면 여전히 여러 노드에 묻는다. 자주 하는 쿼리는 쿼리 표로 만들고, 가끔 하는 쿼리에 인덱스를 쓴다

넣기는 덮어쓰기

INSERT INTO orders_by_user (user_id, order_time, item, qty) VALUES (1, '2026-11-01 10:00:00+0000', 'grape', 9);
-- 같은 기본 키의 apple 행이 오류 없이 grape 로 바뀌었다

UPDATE orders_by_user SET qty = 5 WHERE user_id = 3 AND order_time = '2026-11-07 08:00:00+0000';
-- 없던 행이 생겼다 (item 은 null)

INSERT INTO orders_by_user (user_id, order_time, item, qty) VALUES (2, '2026-11-03 12:00:00+0000', 'xx', 0) IF NOT EXISTS;
 [applied] | user_id | order_time                      | item | qty
-----------+---------+---------------------------------+------+-----
     False |       2 | 2026-11-03 12:00:00.000000+0000 | milk |   2
  • INSERT 와 UPDATE 는 둘 다 "이 키에 이 값을 쓴다" 다. 있으면 바꾸고 없으면 만든다. 기본 키가 겹치면 알리지 않고 덮는다
  • 없을 때만 넣으려면 IF NOT EXISTS 를 붙인다. 이미 있으면 [applied] False 와 있던 행이 온다. 노드끼리 합의를 거치므로(경량 트랜잭션) 느리다. 노드 셋 · QUORUM 에서 cqlsh 로 1000 개를 넣자 보통 쓰기 3.7 초, IF NOT EXISTS 12.0 초였다. 꼭 필요한 곳(가입 아이디) 에만 쓴다

TTL

INSERT INTO orders_by_user (user_id, order_time, item, qty) VALUES (4, '2026-11-08 08:00:00+0000', 'tmp', 1) USING TTL 5;
SELECT item, TTL(item), WRITETIME(item) FROM orders_by_user WHERE user_id = 4;
 item | ttl(item) | writetime(item)
------+-----------+------------------
  tmp |         5 | 1794200122039090
  • 6 초 뒤에 같은 SELECT 는 (0 rows) 였다
  • WRITETIME 은 그 값을 쓴 시각(마이크로초) 이다. 노드마다 값이 다르면 이 시각이 늦은 쪽이 이긴다. 그래서 노드의 시계를 NTP 로 맞춘다
  • 지운 행 · 만료된 행은 바로 사라지지 않고 표시(tombstone) 로 남았다가 나중에 치워진다. 지우기가 잦은 파티션은 읽기가 느려진다. 자주 지울 자료는 TTL 로 두고 파티션을 날짜로 나눈다
