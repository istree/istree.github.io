MongoDB 는 컬렉션에 문서를 넣고, 조건을 문서로 적어 찾는다. 표를 미리 만들지 않아도 첫 insertOne 에서 DB · 컬렉션이 생긴다. 문서마다 필드가 달라도 되므로, 같은 필드에 숫자와 글자가 섞여도 넣을 때는 아무 말이 없다. 찾을 때 덜 찾아질 뿐이다. 고칠 때는 $set · $inc 같은 연산자로 필드만 바꾸고, 모아 셀 때는 단계를 이어 붙인 aggregate 를 쓴다. 자주 찾는 필드에는 인덱스를 만들고, explain 으로 인덱스를 쓰는지 본다. 아래 예제는 mongo:9(9.0.4) 컨테이너의 mongosh 에서 돌렸다.

넣기

use shop
db.orders.insertOne({ item: "apple", qty: 3, price: 1200, tags: ["fruit"], user: { name: "kim", city: "Seoul" } })
// { acknowledged: true, insertedId: ObjectId('6af14dec0bad7c86a77ef5cc') }
db.orders.insertMany([
  { item: "pear", qty: 1, price: 3000, tags: ["fruit"], user: { name: "lee", city: "Busan" } },
  { item: "milk", qty: 2, price: 2500, tags: ["dairy"], user: { name: "kim", city: "Seoul" } },
  { item: "apple", qty: "5", price: 1200 },
])
  • _id 를 주지 않으면 ObjectId 가 붙는다. 앞 4 바이트가 만든 시각이라 대략 넣은 순서로 늘어난다
  • 넷째 문서는 qty 가 글자 "5" 이고 tags · user 가 없다. 그래도 그대로 들어간다

찾기

db.orders.find({ qty: { $gt: 1 } }, { _id: 0, item: 1, qty: 1 }).sort({ qty: -1 })
// [ { item: 'apple', qty: 3 }, { item: 'milk', qty: 2 } ]
db.orders.find({ "user.city": "Seoul", tags: "fruit" }, { _id: 0, item: 1 })
// [ { item: 'apple' } ]
db.orders.countDocuments({ item: { $in: ["apple", "pear"] } })
// 3
조건 뜻
{ qty: 3 } 같다
{ qty: { $gt: 1 } } · $gte · $lt · $ne 크다 · 크거나 같다 · 작다 · 다르다
{ item: { $in: [...] } } 그 가운데 하나
{ "user.city": "Seoul" } 안쪽 문서의 필드 (점으로 연결하고 따옴표로 감싼다)
{ tags: "fruit" } 배열에 그 값이 들어 있다
{ qty: { $type: "string" } } 그 자료형이다
  • 둘째 인자는 돌려받을 필드다(1 은 넣고 0 은 뺀다). _id 는 빼라고 하지 않으면 늘 온다
  • qty: "5" 문서는 $gt: 1 에 걸리지 않았다. 숫자 조건은 숫자 필드만 비교한다. 넣는 쪽에서 자료형을 지키거나 스키마 검사($jsonSchema 검증) 를 건다

고치기

db.orders.updateOne({ item: "pear" }, { $inc: { qty: 1 }, $set: { "user.city": "Daegu" } })
// { acknowledged: true, insertedId: null, matchedCount: 1, modifiedCount: 1, upsertedCount: 0 }
db.orders.updateOne({ item: "pear" }, { qty: 9 })
// MongoInvalidArgumentError: Update document requires atomic operators
db.orders.replaceOne({ item: "milk" }, { item: "milk", qty: 1 })
db.orders.findOne({ item: "milk" }, { _id: 0 })
// { item: 'milk', qty: 1 }      price · tags · user 가 사라졌다
db.orders.updateOne({ item: "grape" }, { $set: { qty: 7 } }, { upsert: true })
// { …, matchedCount: 0, upsertedCount: 1, insertedId: ObjectId('6af14decd697f68b76c0aa74') }
db.orders.deleteMany({ qty: { $type: "string" } })
// { acknowledged: true, deletedCount: 1 }
  • updateOne 에 연산자 없는 문서를 주면 막힌다. 문서를 통째로 바꾸려면 replaceOne 을 쓰고, 그때 적지 않은 필드는 사라진다
  • upsert: true 는 맞는 문서가 없으면 조건과 $set 을 합쳐 새로 넣는다
  • updateMany · deleteMany 는 맞는 문서를 모두 바꾼다. 조건을 {} 로 주면 전부다. 먼저 같은 조건으로 countDocuments 를 해 본다

모아 세기

db.orders.aggregate([
  { $match: { price: { $gte: 1000 } } },
  { $group: { _id: "$item", total: { $sum: "$qty" }, n: { $sum: 1 } } },
  { $sort: { total: -1 } },
])
// [ { _id: 'apple', total: 7, n: 2 }, { _id: 'pear', total: 4, n: 2 } ]
단계 SQL 로 치면
$match WHERE
$group GROUP BY (_id 가 묶는 값, "$필드" 로 필드를 가리킨다)
$sort · $limit ORDER BY · LIMIT
$project SELECT 의 열
$lookup LEFT JOIN
$unwind 배열을 원소마다 한 문서로 편다
  • 단계는 차례로 돈다. $match 를 앞에 두면 그 뒤 단계가 다룰 문서가 줄고, 인덱스도 쓴다

인덱스

문서 10 만 개를 넣고 이메일로 찾았다.

db.users.find({ email: "u77777@ex.com" }).explain("executionStats")
단계 본 문서 걸린 시간
인덱스 없이 COLLSCAN 100000 22 ms
createIndex({ email: 1 }, { unique: true }) 뒤 EXPRESS_IXSCAN 1 1 ms 
db.users.insertOne({ email: "u1@ex.com" })
// E11000 duplicate key error collection: shop.users index: email_1 dup key: { email: "u1@ex.com" }

여러 필드로 찾고 줄 세우면 복합 인덱스를 만든다.

db.users.find({ city: "Busan", age: { $gte: 60 } }).sort({ age: 1 })
db.users.createIndex({ city: 1, age: 1 })
단계 본 문서
인덱스 없이 SORT · COLLSCAN 100000
{ city: 1, age: 1 } 뒤 FETCH · IXSCAN 6667 (돌려준 수와 같다)
같은 인덱스로 { age: 30 } 만 COLLSCAN 100000
  • 복합 인덱스는 앞 필드부터 쓴다. age 만으로 찾을 때는 { city, age } 인덱스를 쓰지 못했다. 같음 조건 필드를 앞에, 범위 · 정렬 필드를 뒤에 둔다
  • SORT 단계가 보이면 메모리에서 줄 세운 것이다. 인덱스 순서로 읽으면 이 단계가 없어진다
  • 인덱스 목록은 db.users.getIndexes() 다(_id_ · email_1 · city_1_age_1). 인덱스는 쓰기마다 함께 고쳐지므로 쓰지 않는 것은 지운다(dropIndex)
