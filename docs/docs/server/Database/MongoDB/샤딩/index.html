샤딩은 한 컬렉션의 문서를 여러 복제 세트(샤드) 에 나눠 담는 것이다. 문서마다 샤드 키 값을 보고 어느 샤드에 둘지 정한다. 앱은 샤드에 바로 붙지 않고 라우터(mongos) 에 붙는다. mongos 는 설정 서버가 가진 "어느 키 범위가 어느 샤드에" 표를 보고 요청을 보낸다. 자료나 쓰기가 한 복제 세트에 담기지 않을 때 쓰고, 샤드 키를 잘못 고르면 한 샤드만 바빠진다. 아래 예제는 mongo:9(9.0.4) 컨테이너 넷 — 설정 서버 cfg1, 샤드 sh1 · sh2, 라우터 mongos — 로 돌렸다. 세 mongod 는 저마다 노드 하나짜리 복제 세트이고, 운영에서는 저마다 노드 셋으로 둔다.

띄우기

# 셋 모두 열쇠 파일을 붙인다 (복제 세트와 같다)
docker run -d --name cfg1 --hostname cfg1 --network mongo-net -v mongo-key:/key:ro \
  mongo:9 mongod --configsvr --replSet cfg --port 27017 --bind_ip_all --keyFile /key/keyfile
docker run -d --name sh1 --hostname sh1 --network mongo-net -v mongo-key:/key:ro \
  mongo:9 mongod --shardsvr --replSet sh1 --port 27017 --bind_ip_all --keyFile /key/keyfile
docker run -d --name sh2 …   # sh1 과 같이 --replSet sh2

docker exec cfg1 mongosh --eval 'rs.initiate({_id: "cfg", configsvr: true, members: [{_id: 0, host: "cfg1:27017"}]})'
docker exec sh1 mongosh --eval 'rs.initiate({_id: "sh1", members: [{_id: 0, host: "sh1:27017"}]})'
docker exec sh2 mongosh --eval 'rs.initiate({_id: "sh2", members: [{_id: 0, host: "sh2:27017"}]})'

docker run -d --name mongos --hostname mongos --network mongo-net -v mongo-key:/key:ro \
  mongo:9 mongos --configdb cfg/cfg1:27017 --bind_ip_all --keyFile /key/keyfile
// mongos 에서 — 첫 사용자를 만들고 그 사용자로 다시 붙는다
db.getSiblingDB("admin").createUser({ user: "root", pwd: "Root-pass-1", roles: ["root"] })
sh.addShard("sh1/sh1:27017")
sh.addShard("sh2/sh2:27017")
db.adminCommand({ listShards: 1 }).shards.map(s => s._id + " " + s.host)
// [ 'sh1 sh1/sh1:27017', 'sh2 sh2/sh2:27017' ]
  • --shardsvr · --configsvr 는 기본 포트가 27018 · 27019 다. 위처럼 --port 27017 을 주거나 그 포트로 적는다
  • mongos 에서 만든 사용자는 설정 서버에 담긴다. 샤드의 mongod 에 그 사용자로 바로 붙으면 MongoServerError: Authentication failed. 다. 앱 · 관리 모두 mongos 를 거친다
  • 앱의 연결 문자열은 mongos 를 가리킨다(mongodb://…@mongos:27017/?authSource=admin). mongos 는 자료가 없어 여럿 띄워 두고 함께 적는다

컬렉션 나누기

sh.shardCollection("shop.orders", { userId: "hashed" })
// 문서 2 만 개를 넣고
db.orders.getShardDistribution()
Shard sh1 at sh1/sh1:27017
{ data: '558KiB', docs: 9860, chunks: 1, … }
Shard sh2 at sh2/sh2:27017
{ data: '574KiB', docs: 10140, chunks: 1, … }
Totals
{ data: '1.1MiB', docs: 20000, chunks: 2,
  'Shard sh1': [ '49.3 % data', … ], 'Shard sh2': [ '50.7 % data', … ] }
  • 해시 키는 키 값을 해시해 범위를 나누므로, 늘어나는 userId 도 두 샤드에 고르게 갔다
  • 컬렉션은 덩어리(chunk) 로 나뉘고, 덩어리마다 키 범위와 샤드가 정해진다. 덩어리가 고르지 않으면 balancer 가 저절로 옮긴다

찾을 때

db.orders.find({ userId: 42 }).explain()   // 샤드 sh2 | stage SINGLE_SHARD
db.orders.find({ item: "x" }).explain()    // 샤드 sh1,sh2 | stage SHARD_MERGE
  • 조건에 샤드 키가 있으면 mongos 가 그 샤드 하나에만 묻는다
  • 샤드 키가 없으면 모든 샤드에 묻고 결과를 모은다(scatter-gather). 샤드가 늘수록 느려지므로, 가장 자주 하는 쿼리의 조건 필드를 샤드 키로 고른다

샤드 키 선택

늘어나는 시각(at) 을 범위 키로 쓴 events 컬렉션에 새 문서 5000 개를 넣었다. 덩어리 크기를 1 MB 로 줄여 덩어리가 여럿으로 나뉘고 옮겨진 뒤였다.

컬렉션 · 샤드 키 새 문서 5000 개가 간 곳
events · { at: 1 } (범위) sh1 에 5000 · sh2 에 0
orders · { userId: "hashed" } sh1 에 2463 · sh2 에 2537
  • 범위 키가 늘어나는 값이면 새 문서는 늘 마지막 덩어리(at 의 끝, maxKey 까지) 로 간다. 그 덩어리를 가진 샤드 하나가 모든 쓰기를 받는다. 옛 덩어리는 balancer 가 옮겨도 새 쓰기는 고르게 퍼지지 않는다
  • 해시 키는 쓰기가 고르게 퍼지지만, 키 범위로 찾기(at 이 어제부터 오늘까지) 는 모든 샤드에 묻는다
볼 것 좋은 키
값의 가짓수 많다 (사용자 id). country 처럼 몇 가지뿐이면 덩어리를 더 나누지 못한다
값마다 문서 수 고르다. 한 값에 문서가 몰리면 그 덩어리가 커진다
늘어나기 늘어나는 값(시각 · ObjectId) 은 해시로 쓰거나 앞에 다른 필드를 붙인다({ userId: 1, at: 1 })
쿼리 자주 하는 쿼리의 조건에 들어 있다
  • 5.0 부터 reshardCollection 으로 샤드 키를 바꿀 수 있다. 다만 컬렉션 전체를 다시 나누는 무거운 일이라 처음에 고르는 편이 낫다
