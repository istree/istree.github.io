PostgreSQL 의 백업은 대개 pg_dump 로 DB 하나를 파일로 떠 두는 것이다. 평문(SQL) 으로 뜨면 psql 로 넣고, 자체 꼴(-Fc) 로 뜨면 pg_restore 로 넣는다. 자체 꼴은 압축되고, 표 하나만 골라 넣거나 넣기 전에 지우는 일을 복원할 때 정할 수 있어 서버 백업에는 이쪽을 쓴다. role(사용자) 은 DB 밖에 있어 pg_dump 에 들어가지 않으므로 pg_dumpall --globals-only 로 따로 뜬다. 아래 예제는 PostgreSQL 16.15(Ubuntu 패키지) 에서 뜨고, postgres:18(18.6) 컨테이너에 넣어 봤다.

뜨기

sudo -u postgres pg_dump shop > shop.sql            # 평문 — 3013 바이트
sudo -u postgres pg_dump -Fc shop > shop.dump       # 자체 꼴 — 7874 바이트 (작은 DB 라 오히려 크다)
sudo -u postgres pg_dump -Fd -j 2 -f shopdir shop   # 폴더 꼴 — 표마다 파일, 여럿을 함께 뜬다
sudo -u postgres pg_dumpall --globals-only > globals.sql   # role · 테이블스페이스

shop.sql 의 중심은 표를 만들고 자료를 넣는 SQL 이다. 자료는 INSERT 가 아니라 COPY 로 들어간다.

CREATE TABLE public.orders (
    id integer NOT NULL,
    item text,
    qty integer
);
ALTER TABLE public.orders OWNER TO app;
ALTER TABLE public.orders ALTER COLUMN id ADD GENERATED ALWAYS AS IDENTITY (
    SEQUENCE NAME public.orders_id_seq
    …
);
COPY public.orders (id, item, qty) FROM stdin;
옵션 뜻
-Fc 자체 꼴 (압축, pg_restore 로 넣는다)
-Fd -j N 폴더 꼴, N 개를 함께 뜬다. 큰 DB 에 쓴다
-t orders · -T log 그 표만 · 그 표를 빼고
-n app 그 스키마만
--no-owner · --no-acl 주인 · 권한 줄을 넣지 않는다
-s · -a 표 구조만 · 자료만
  • pg_dump 는 한 시점의 모습으로 뜬다. 뜨는 동안에도 서비스가 계속 쓴다
  • pg_restore -l shop.dump 로 파일 안의 목록(표 · 자료 · 권한) 을 본다
  • 평문 덤프 앞뒤에 \restrict 열쇠 · \unrestrict 열쇠 줄이 있다(16.15 · 18.6 모두). 덤프 안에 숨은 psql 명령이 돌지 못하게 막는 줄로, 2025 년 보안 업데이트에서 생겼다. 그보다 옛 psql(16.9) 로 넣으면 invalid command \restrict 가 나온다

복원

createdb shop
pg_restore -d shop shop.dump
넣는 곳 결과
DB 가 없을 때 psql shop < shop.sql FATAL: database "shop" does not exist — 먼저 createdb
role 이 없는 서버에 평문 ERROR: role "app" does not exist 가 줄마다 나고 표 주인은 postgres 가 된다 (자료는 들어간다)
role 이 없는 서버에 pg_restore pg_restore: warning: errors ignored on restore: 8 — 같은 까닭
globals.sql 을 먼저 넣은 뒤 pg_restore 오류 없이 표 주인이 app 으로 돌아온다
pg_restore --no-owner --no-acl 오류 없이, 넣은 role(postgres) 이 주인이 된다 
pg_restore -d shop --clean --if-exists shop.dump   # 있는 표를 지우고 다시 넣는다
pg_restore -C -d postgres shop.dump                # DB 를 만들면서 넣는다 (-d 는 붙을 DB)
pg_restore -t orders -f - shop.dump                # orders 만 SQL 로 꺼내 본다
  • globals.sql 을 새 서버에 넣으면 ERROR: role "postgres" already exists 한 줄이 나온다. 이미 있는 관리자 role 이라 괜찮다
  • --clean 은 복원 대상 DB 의 같은 이름 표를 지운다. 귤 을 더한 표에 다시 넣자 덤프 때의 두 행으로 돌아갔다. 운영 DB 에 넣기 전에 새 DB 에 먼저 넣어 본다
  • 큰 DB 는 pg_restore -j 4 로 여럿을 함께 넣는다 (자체 · 폴더 꼴만)

판이 다를 때

새 판 서버에 옛 판의 덤프를 넣는 것은 된다(16 → 18). 거꾸로는 막힌다.

# 18 에서 뜬 평문을 16 에 넣으면
ERROR:  unrecognized configuration parameter "transaction_timeout"
# 18 에서 뜬 자체 꼴을 16 의 pg_restore 로 넣으면
pg_restore: error: unsupported version (1.16) in file header
  • 판을 올릴 때는 새 판의 pg_dump 로 옛 서버에서 뜬다. pg_dump 는 자기보다 옛 서버에서 뜰 수 있다
  • 같은 서버에서 판을 올릴 때는 덤프 대신 pg_upgradecluster 16 main(Ubuntu) 이나 pg_upgrade 를 쓴다

Docker 에서

docker exec pg pg_dump -U postgres -Fc shop > shop.dump
docker exec -i pg pg_restore -U postgres -d shop < shop.dump    # -i 가 있어야 파일이 들어간다
docker exec pg pg_dumpall -U postgres --globals-only > globals.sql

매일 뜨기

#!/bin/bash
# /usr/local/bin/pg-backup.sh — postgres 사용자의 crontab 에서 돈다
set -euo pipefail
d=/var/backups/postgresql
pg_dump -Fc shop > $d/shop-$(date +%F).dump
pg_dumpall --globals-only > $d/globals-$(date +%F).sql
find $d -name "*.dump" -mtime +14 -delete
find $d -name "globals-*.sql" -mtime +14 -delete
# sudo -u postgres crontab -e
30 3 * * * /usr/local/bin/pg-backup.sh >> /var/log/postgresql/backup.log 2>&1
  • 폴더는 먼저 만들어 postgres 에게 준다(sudo install -d -o postgres -m 700 /var/backups/postgresql)
  • postgres 사용자로 돌리면 peer 방식으로 들어가 비밀번호가 필요 없다. 다른 사용자로 돌린다면 ~/.pgpass 를 쓴다
  • 덤프는 뜬 시점으로만 돌아간다. 그 사이의 변경까지 살리려면 WAL 을 모아 두는 방식(pg_basebackup · 시점 복구) 을 쓴다
