MariaDB 의 백업은 두 가지다. mariadb-dump 는 DB 를 SQL 파일로 뜨고(MySQL 의 mysqldump 와 같은 옵션), mariadb-backup 은 자료 폴더의 파일을 서비스를 멈추지 않고 통째로 뜬다. 작은 DB · 다른 서버로 옮기기에는 덤프를, 큰 DB 를 빨리 되살려야 할 때는 mariadb-backup 을 쓴다. 사용자 · 권한은 mariadb-dump --system=users 로 SQL 로 뜬다. 아래 예제는 Ubuntu 패키지의 MariaDB 10.11.14 와 mariadb:12.3(12.3.3) 컨테이너에서 돌렸고, mysql:8.4(8.4.13) 와 서로 덤프를 넣어 봤다.

mariadb-dump

sudo mariadb-dump --single-transaction --routines --triggers shop > shop.sql
sudo mariadb-dump --single-transaction shop | gzip > shop.sql.gz     # 12.3 의 shop 에서 2827 바이트 → 900 바이트
sudo mariadb shop < shop.sql
  • 옵션은 mysqldump 와 같다. Ubuntu 패키지에서는 mysqldump 이름도 되지만 mariadb:12.3 이미지에는 mariadb-dump 만 있다
  • sudo 로 돌리면 root 가 unix_socket 으로 들어가 비밀번호가 필요 없다

덤프의 첫 줄은 이렇다.

/*M!999999\- enable the sandbox mode */
  • 덤프를 넣는 mariadb 클라이언트를 샌드박스로 바꾸는 줄이다. 덤프 안에 셸 명령(\! …) 이 숨어 있어도 돌지 못하게 막는다. 2024 년 5 월 보안 업데이트에서 생겼다
  • 덤프 중간에 \! echo pwned 를 끼워 10.11 클라이언트로 넣자 ERROR at line 1: Not allowed in the sandbox mode 로 멈췄다. 첫 줄이 없는 파일에서는 명령이 돌았다
  • M! 은 MariaDB 만 읽는 주석이다. MySQL 8.4 클라이언트는 이 줄을 오류 없이 넘겼고, 끼워 둔 명령은 돌았다. 남이 준 덤프는 MariaDB 클라이언트로 넣는다

사용자 옮기기

sudo mariadb-dump --system=users --insert-ignore > users.sql
CREATE USER IF NOT EXISTS `app`@`%` IDENTIFIED BY PASSWORD '*95B7D082CF2B4B751337D4A78D327D07811EE287';
CREATE USER IF NOT EXISTS `e`@`%` IDENTIFIED VIA ed25519 USING 'AHKSLYUnuwgrJfPysylC7zyaOfGm7t3wiTtBnqS8e2E';
GRANT ALL PRIVILEGES ON `shop`.* TO `app`@`%`;
GRANT `reader` TO `report`@`%`;
/*M!100005 SET DEFAULT ROLE 'reader' FOR 'report'@'%' */;

새 mariadb:12.3 서버에 넣어 본 결과다.

넣은 것 결과
--insert-ignore 없이 ERROR 1396 (HY000) at line 18: Operation CREATE USER failed for 'mariadb.sys'@'localhost' — 새 서버에도 있는 계정에서 멈춘다
ed25519 계정이 있는데 플러그인을 깔지 않고 ERROR 1524 (HY000) at line 25: Plugin 'ed25519' is not loaded — 그 뒤의 권한 · 역할이 들어가지 않는다
새 서버에 INSTALL SONAME 'auth_ed25519' 뒤 오류 없이 들어가고, report 는 역할까지 켜진 채 붙는다
  • 계정 · 권한 · 역할 · 기본 역할이 함께 들어간다. mariadb.sys · root · healthcheck 같은 시스템 계정도 들어 있다
  • root 의 비밀번호가 옛 서버의 것으로 바뀐다. GRANT … TO root … IDENTIFIED BY PASSWORD '…' 줄 때문이다. 새 서버의 root 비밀번호로는 Access denied 였고 옛 비밀번호로 들어갔다
  • 플러그인도 --system=plugins 로 뜰 수 있지만 새 서버에 이미 있는 플러그인이면 오류다(11.8.9 에서는 넣을 때 문법 오류였다). 필요한 플러그인은 손으로 먼저 깐다

mariadb-backup

Ubuntu 패키지에서는 mariadb-backup 을 따로 깐다.

sudo apt install mariadb-backup
sudo mkdir -p /var/backups/mariadb
sudo mariadb-backup --backup --target-dir=/var/backups/mariadb/full    # 18 MB
sudo mariadb-backup --prepare --target-dir=/var/backups/mariadb/full
  • --backup 은 자료 파일과, 뜨는 동안 쌓인 기록(redo log) 을 함께 뜬다. --prepare 가 그 기록을 파일에 반영해 한 시점의 모습으로 맞춘다. 되살리기 전에 꼭 한 번 돌린다
  • 끝에 completed OK! 가 나와야 됐다. 위 폴더(/var/backups/mariadb) 가 없으면 Error: cannot mkdir 2: /var/backups/mariadb/full/ 로 멈춘다 — 마지막 폴더만 만든다
  • 폴더 안에는 DB 마다 폴더 · ibdata1 · ib_logfile0 과 뜬 시점의 정보 파일(xtrabackup_info, 12.3 은 mariadb_backup_info) 이 있다
  • 옵션의 -h 는 호스트가 아니라 자료 폴더(--datadir) 다. 호스트는 --host(-H) 로 준다. 다만 자료 폴더를 읽어야 하므로 서버와 같은 기계에서 돌린다

되살리기는 서버를 멈추고 빈 자료 폴더에 파일을 넣는다.

sudo systemctl stop mariadb
sudo mv /var/lib/mysql /var/lib/mysql.old
sudo mkdir /var/lib/mysql
sudo mariadb-backup --copy-back --target-dir=/var/backups/mariadb/full
sudo chown -R mysql:mysql /var/lib/mysql
sudo systemctl start mariadb
  • 자료 폴더가 비어 있지 않으면 Original data directory /var/lib/mysql is not empty! 로 거부한다
  • 넣은 파일의 주인은 root 다. chown 없이 띄우자 서버가 뜨지 않았다(…fail!)
  • 뜬 뒤에 넣은 행은 되살린 DB 에 없었다. 뜬 시점으로 돌아간다

Docker 에서

덤프는 docker exec 로 뜨고 넣는다.

docker exec mdb mariadb-dump -uroot -pRoot-pass-1 --single-transaction shop > shop.sql
docker exec -i mdb mariadb -uroot -pRoot-pass-1 shop < shop.sql     # -i 가 있어야 파일이 들어간다

mariadb-backup 은 백업용 볼륨을 함께 붙여 둔다.

docker run -d --name mdb -e MARIADB_ROOT_PASSWORD=Root-pass-1 \
  -v mariadb-data:/var/lib/mysql -v mariadb-backup:/backup mariadb:12.3
docker exec mdb mariadb-backup --backup --target-dir=/backup/full -uroot -pRoot-pass-1
docker exec mdb mariadb-backup --prepare --target-dir=/backup/full

# 새 볼륨에 되살려 새 컨테이너로 띄운다
docker run --rm -v mariadb-new:/var/lib/mysql -v mariadb-backup:/backup mariadb:12.3 \
  bash -c 'mariadb-backup --copy-back --target-dir=/backup/full && chown -R mysql:mysql /var/lib/mysql'
docker run -d --name mdb2 -v mariadb-new:/var/lib/mysql mariadb:12.3
  • 컨테이너 안의 root 는 unix_socket 이 아니라 비밀번호 계정이라 -uroot -p… 를 준다
  • 되살린 볼륨으로 띄울 때는 MARIADB_ROOT_PASSWORD 가 없어도 뜬다. 자료 폴더가 비어 있지 않아 초기화를 건너뛰고, root 비밀번호는 뜬 서버의 것이다

MySQL 과 서로 옮기기

덤프에는 표마다 정렬 규칙이 적혀 있고, 그 이름을 모르는 서버에서 막힌다.

덤프 → 넣는 곳 결과
MySQL 8.4 → MariaDB 10.11 ERROR 1273 (HY000) at line 25: Unknown collation: 'utf8mb4_0900_ai_ci'
MySQL 8.4 → MariaDB 12.3 들어간다 — 12.3 은 utf8mb4_0900_ai_ci 를 안다
MariaDB 12.3 → MySQL 8.4 ERROR 1273 (HY000) at line 26: Unknown collation: 'utf8mb4_uca1400_ai_ci'
MariaDB 12.3 → MariaDB 10.11 들어간다

정렬 규칙 이름을 넣는 곳이 아는 것으로 바꿔 넣는다.

sed 's/utf8mb4_0900_ai_ci/utf8mb4_unicode_520_ci/g' mysql.sql | sudo mariadb shop          # MySQL → MariaDB 10.11
sed 's/utf8mb4_uca1400_ai_ci/utf8mb4_0900_ai_ci/g' mariadb.sql | mysql -u root -p shop   # MariaDB → MySQL
  • 두 줄 모두 오류 없이 들어가고 한글이 그대로였다
  • 오류가 난 줄 앞의 표는 이미 들어가 있다. 고친 덤프는 빈 DB 에 다시 넣는다

매일 뜨기

#!/bin/bash
# /usr/local/bin/mariadb-backup.sh — root 의 crontab 에서 돈다
set -euo pipefail
umask 077                 # 덤프에 비밀번호 해시가 있어 root 만 읽게 한다
d=/var/backups/mariadb
mariadb-dump --single-transaction --routines --triggers --all-databases | gzip > $d/all-$(date +%F).sql.gz
mariadb-dump --system=users --insert-ignore > $d/users-$(date +%F).sql
find $d -name "*.gz" -mtime +14 -delete
find $d -name "users-*.sql" -mtime +14 -delete
# sudo crontab -e
30 3 * * * /usr/local/bin/mariadb-backup.sh >> /var/log/mariadb-backup.log 2>&1
  • root 로 돌리면 unix_socket 으로 들어가 비밀번호 파일이 필요 없다
  • umask 없이 돌리자 파일이 -rw-r--r-- 로 생겨 누구나 읽었다. 넣은 뒤에는 -rw------- 였다
  • 덤프는 뜬 시점으로만 돌아간다. 그 사이의 변경까지 살리려면 바이너리 로그(log_bin) 를 켜 두고 덤프 뒤의 로그를 mariadb-binlog 으로 다시 넣는다
